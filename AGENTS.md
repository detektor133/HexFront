# AGENTS.md — правила для AI-агента

Этот файл обязателен к прочтению перед любой работой в репозитории.

## 0. Начало и конец каждой сессии

- **Начало:** прочитай `docs/STATUS.md` (где остановились), текущий этап, `docs/DECISIONS.md` (последние 10 строк), `docs/QUESTIONS.md`.
- **Конец:** обнови `docs/STATUS.md` (что сделано, что дальше, блокеры), закоммить, запушь ветку и дождись зелёного CI в GitHub (скилл `$ci`).
- Изменения документации и этапов — строго по `docs/PROCESS.md`.
- Команды владельца: `$task <NN/Tn>` — задача, `$next` — следующая задача этапа, `$split <NN/Tn>` — разбить большую задачу, `$accept <NN/Tn>` — приёмочные матчи после коммита, `$bug <описание>` — записать баг, `$decide` — записать решения в доки, `$stage-close` — закрыть этап, `$ci` — проверить CI. Скиллы лежат в `.agents/skills/`.

## 1. Источник истины

| Вопрос | Где ответ |
| --- | --- |
| Что делает игра, формулы, числа | `docs/gdd/*.md`, числа — только `docs/gdd/10-balance.md` |
| Как выглядит | `docs/art/style-guide.md`, `docs/art/tokens.json` |
| Как устроен код | `docs/architecture/*.md`, `docs/architecture/adr/*` |
| Как тестировать | `docs/testing.md` |
| Git, комментарии, стиль кода | `docs/CONVENTIONS.md` |
| Что делать сейчас | текущий `docs/stages/stage-XX-*.md` |

- **Не выдумывай механики, числа, цвета, шрифты.** Если в доках нет ответа — остановись и запиши вопрос в `docs/QUESTIONS.md`, продолжай другие задачи.
- **Не меняй доки по своей инициативе.** Предложение → `docs/CHANGELOG-proposals.md` (что, почему, какие файлы затронет).
- **Прямое поручение владельца в чате** («поменяй X на Y») — разрешение менять доки. Порядок: доки → код → тесты → строка в `DECISIONS.md`, один коммит `change:`/`balance:`. Найди **все** упоминания изменяемого правила (grep по терминам и константам), а не только первое.
- Если поручение противоречит другим разделам доков — сначала перечисли конфликты владельцу, потом делай.
- Делай только объём текущего этапа. Порядок задач — строка «Очередь» в `STATUS.md`; найденный баг — в `docs/BUGS.md`, в текущей задаче чинится только Б1. Раздел «Вне объёма» в этапе — запрет, а не пожелание.

## 2. Стек (зафиксирован, см. ADR)

- TypeScript 5.x, `strict: true`, `noUncheckedIndexedAccess: true`, `exactOptionalPropertyTypes: true`.
- pnpm workspaces, Node 22 LTS.
- `packages/sim` — чистая симуляция, **ноль runtime-зависимостей**.
- `packages/protocol` — типы сообщений клиент/сервер, кодеки.
- `apps/server` — Node, `ws`.
- `apps/client` — Vite, PixiJS v8 (карта), React 19 (меню/HUD/карточки).
- Тесты: Vitest, fast-check, Playwright (скриншоты).
- **Новые зависимости — только с записью в `docs/architecture/adr/`**. Запрещены: state-менеджеры (Redux, MobX, Zustand), ECS-библиотеки, UI-киты (MUI, shadcn, Chakra), CSS-фреймворки (Tailwind), lodash.

## 3. Железные правила симуляции (`packages/sim`)

1. Симуляция — функция `step(state, commands): state` (мутирующая внутри себя, но детерминированная). Тик = 100 мс (10 Гц).
2. **Только целые числа.** Все дробные величины — fixed-point: `FP = 1000` (1.0 = 1000). Деление только через `fpDiv`/`intDiv` из `packages/sim/src/math`. Запрещены `Math.random`, `Date`, `performance`, `Math.sin/cos/sqrt/pow` и любая float-арифметика с результатом, влияющим на состояние.
3. Порядок итераций стабилен: сущности хранятся в массивах, отсортированных по `id`. Никаких `for…in` по объектам, никаких `Set` с последующим порядкозависимым использованием.
4. `sim` не импортирует ничего из `server`, `client`, `protocol`, Node API, DOM.
5. Любая случайность (генерация карт, боты) — через seeded PRNG из `packages/sim/src/rng.ts`, сид передаётся явно.
6. Каждая механика реализуется **системой** — функцией в `packages/sim/src/systems/`, вызываемой из `step` в порядке, описанном в `docs/architecture/sim-core.md`.

Эти правила проверяются линтером (ESLint `no-restricted-globals`, `no-restricted-properties`) и dependency-cruiser. Не отключай правила через `eslint-disable` — это автоматический провал задачи.

## 4. Процесс работы над задачей

1. Прочитай задачу и критерии приёмки в этапе.
2. Прочитай соответствующие разделы GDD/арта/архитектуры (через `grep -n -C5`, по карте ниже).
3. **Сначала тесты** на критерии приёмки и краевые случаи (см. `docs/testing.md`), убедись, что они падают.
4. Реализуй минимально достаточный код.
5. `pnpm verify` — зелёный (в работе `--changed`, перед коммитом без флага). Не удаляй и не ослабляй чужие тесты, чтобы стало зелёным.
6. Коммит **по-русски** в формате `docs/CONVENTIONS.md`: `feat(sim): добавлена система сетей снабжения` + трейлер `Этап: 02/T7`. Одна задача = один или несколько атомарных коммитов.
7. Отметь задачу в этапе `- [x]`.
8. Запушь ветку этапа и дождись зелёного CI в GitHub (скилл `$ci`, REST API через curl). Красный CI — задача не готова: чини, не переходи к следующей.

## 5. Определение «готово»

- Все критерии приёмки задачи покрыты тестами и проходят.
- `pnpm verify` зелёный, нет `any`, нет `// @ts-ignore`, нет `TODO` без ссылки на задачу.
- Для визуальных задач: эталоны обновлены через `pnpm visual --update`, пути к новым PNG — в отчёте. Картинки агент не открывает, их просматривает владелец.
- Публичные функции `sim` имеют JSDoc по-русски с единицами измерения (`/** @returns fixed-point, людей в секунду */`); комментарии — по правилам `docs/CONVENTIONS.md` §3.

## 6. Стиль кода (кратко; полностью — `docs/CONVENTIONS.md`)

- Коммиты, PR, комментарии, JSDoc, названия тестов — **по-русски**; идентификаторы и ветки — латиницей.
- Комментарий объясняет «почему», а не «что». Запрещены закомментированный код, «разговорные» комментарии, `TODO` без `(stage-XX/Tn)`.
- Функции ≤ 60 строк, файлы ≤ 400 строк. Больше — дроби.
- Именование: `camelCase` функции/переменные, `PascalCase` типы, `SCREAMING_SNAKE` константы баланса.
- Числа баланса — только из `packages/sim/src/balance.ts`, который 1:1 повторяет `docs/gdd/10-balance.md`. Магические числа в логике запрещены.
- Ошибки: в `sim` невалидная команда **отклоняется** (возврат `Rejected` с причиной), а не бросает исключение. На сервере — логирование + метрика, без падения комнаты.
- Никаких молчаливых `catch {}`.

## 7. Визуал — анти-«нейросетевые» правила (кратко, полностью в `docs/art/`)

Запрещено без явного разрешения в стайл-гайде:
- градиенты, glassmorphism, blur, неон, тени-свечения;
- шрифты Inter, Roboto, системные по умолчанию; эмодзи в UI;
- фиолетово-синие «tech» палитры, тёмный UI по умолчанию;
- скругления больше указанных в токенах;
- любые растровые картинки, сгенерированные нейросетью.

Все цвета — только из `docs/art/tokens.json`. Все размеры знаков армий — из `docs/art/units.md`.

## 8. Отчёт в конце этапа

Файл `docs/reports/stage-XX.md` (скилл `$stage-close`): что сделано по задачам, что отклонено/перенесено и почему, открытые вопросы, пути к скриншотам, итог `pnpm verify`, известные риски.

## Команды проверки

| Команда | Что делает |
| --- | --- |
| `pnpm verify [--changed]` | **основная проверка**: build → типы → lint → тесты → visual; лог в `.ai-logs/verify-*.log`, в консоль итог ≤ 20 строк |
| `pnpm ai-check --changed` | быстрая проверка без build и visual |
| `pnpm ai-check --staged` | lint staged-файлов (вызывает хук pre-commit) |
| `pnpm visual` | сравнение скриншотов с эталонами: «прошло/не прошло, X %, область, селекторы» |
| `pnpm visual --update` | осознанно обновить эталоны (`apps/client/tests/visual/baseline/`) |
| `pnpm report:match --seeds N` | N матчей ботов, метрики JSON, графики PNG → `docs/reports/match/`, сводка ≤ 20 строк |
| `pnpm check` | полный прогон с подробным выводом — только для CI, агенту не запускать |

Git-хуки (`.githooks/`, включает `pnpm install`): pre-commit — lint staged; commit-msg — заголовок ≤ 72, допустимые области, трейлер; pre-push — lint и commit-check ветки. Хуки агента (`.codex/hooks.json`): при завершении хода сам запускается `pnpm verify --changed`, пока в дереве есть изменения — красный не даст закончить; ручной `pnpm dev` и Playwright блокируются. `gh` не установлен: CI — через REST API GitHub (curl), скилл `$ci`.

## Правила работы (экономия токенов)

- Поиск: сначала `rg -l` только для имён файлов, затем `rg -n -C2` по 1–2 файлам с `| Select-Object -First 80`.
- Большая задача — `$split`; приёмочные матчи — `$accept` отдельной сессией после коммита.
- **Проверка — только `pnpm verify`** (`--changed` в работе, без флага перед коммитом). Детали ошибок — `grep -n -C3 "FAIL\|error" .ai-logs/<лог>`, а не перезапуск.
- Длинные команды — на переднем плане с `timeout`; без фоновых задач и опроса.
- **Картинки, видео и браузер запрещены.** Визуальную проблему описывать по тексту `pnpm visual`: процент, область x/y/ширина/высота, селекторы элементов.
- Независимые команды объединять в один вызов.
- Читать через `grep -n` с контекстом; файл целиком — только тот, что правишь.
- Многострочный текст (коммит, отчёт, файл) — через временный файл, не heredoc.
- Дизайн-вопросы — одним списком и остановиться; код до ответа не начинать.
- Отчёт в чате — до 10 строк со ссылкой на `docs/reports/`; все ответы владельцу — по-русски.
- Сгенерированные файлы токенов (`apps/client/src/theme/tokens.*`) не форматировать prettier — `pnpm tokens`.
- Одна задача — одна сессия; `STATUS.md` обновлять в конце, коммит, push, дождаться CI.
