# AGENTS.md — правила для AI-агента

Этот файл обязателен к прочтению перед любой работой в репозитории.

## 0. Начало и конец каждой сессии

- **Начало:** прочитай `docs/STATUS.md` (где остановились), текущий этап, `docs/DECISIONS.md` (последние 10 строк), `docs/QUESTIONS.md`.
- **Конец задачи:** рабочие роли не меняют статус и не push. После финального review оркестратор или ведущая ручная сессия push-ит код, ждёт зелёный CI точного SHA, затем обновляет `docs/STATUS.md`, создаёт служебный docs-коммит, push-ит его и ждёт его CI.
- **Коммерческий веб-релиз — 2026-11-08.** Релизный контур — все требования этапов 07–10 без сокращения до MVP. Срок не разрешает выкидывать критерии: он требует дробить работу до одного проверяемого механизма и немедленно устранять потери цикла.
- Изменения документации и этапов — строго по `docs/PROCESS.md`.
- Команды владельца: `$task <NN/Tn>` — задача, `$next` — следующая задача этапа, `$plan <NN/Tn>` — перепроверить текст уже существующей задачи роли `plan`, `$plan <текст владельца>` — превратить сырой текст в задачу(и) этапа той же ролью, `$spec <NN/Tn>` — ручная отдельная подготовка приёмочных тестов, `$split <NN/Tn>` — разбить большую задачу (только по решению владельца), `$accept <NN/Tn>` — приёмочные матчи после коммита, `$bug <описание>` — записать баг, `$decide` — записать решения в доки, `$stage-close` — закрыть этап, `$ci` — проверить CI, `$review <NN/Tn>` — read-only ревью с JSON-исходом и атомарными пунктами `КОД`/`ТЕСТ`, `$done <NN/Tn> [слова владельца]` — владелец сделал свою задачу или проверку. Скиллы лежат в `.agents/skills/`.
- Агентный цикл `pnpm agent:run` работает последовательно в ветке этапа: `plan` → один исполнитель реализует код и тесты задачи → целевые тесты и `pnpm verify --changed` → полный `pnpm check` → review по полной матрице → один пакет всех замечаний `КОД:` и `ТЕСТ:` тому же исполнителю (`ПЛАН:` отдельно) → узкий review пакета → повторный полный `pnpm check` → финальный review → один сводный коммит задачи → локальный `pnpm verify:prepush` → **визуальный гейт для UI-задач** → push → CI точного SHA → отметка `[x]` оркестратором. После каждого рабочего коммита цикл проверяет все тесты задачи из общего diff, а не только файлы последнего патча. Красный результат возвращается исполнителю вместе с фактической ошибкой. Отдельный `$spec` запускается только по явному вызову владельца. Reviewer называет тип дефекта, но не разбивает работу между двумя сессиями. Красный pre-push gate запрещает push.
- Незакоммиченная работа исполнителя остаётся привязана к активной задаче: цикл запоминает её пути и сам продолжает её после красного теста, включая перезапуск процесса. Каждая рабочая сессия и reviewer получают точный текст задачи и исходное поручение владельца; замечания reviewer проверяются заново. Красное форматирование цикл исправляет только в сохранённых файлах задачи, исключая сгенерированные токены, и повторяет проверки. Если проверки зелёные, но исполнитель повторно не создал коммит, оркестратор сохраняет только файлы задачи локальным коммитом до review. Остальной повторный красный результат до коммита диагностирует read-only reviewer по фактическому выводу целевых тестов и `pnpm verify --changed`, возвращает конкретный `КОД:`/`ТЕСТ:` тому же исполнителю. Если та же ошибка осталась после следующей попытки, исполнитель меняет способ подготовки состояния или механизм; при новой ошибке переделка не навязывается. Чужой изменённый путь останавливает продолжение; ошибка тестовой фикстуры не создаёт Issue `$decide`.
- **Визуальный гейт.** Ручной браузер, картинки и видео в работе запрещены (см. §«Правила работы»), кроме этого одного автоматического шага: перед push для задачи, тронувшей `apps/client/src/{dev,match,render,theme}/**`, цикл снимает Playwright-скриншоты состояния задачи из её изменённого `@layout`-сценария и HUD на 360/1024/1920 px (`pnpm test:e2e:visual`), затем зовёт `$review` один раз, **прикладывая снимки как изображения `codex exec -i <file>`**. Если критерий требует `@layout`, а сценария или снимка нет, это дефект теста. Гейт ловит искажение и нахлёст, которые геометрические ассерты не видят, один раз за полный проход.
- **Эскалация от точечного патча к переделке.** Цикл отслеживает повторные дефекты после правок одного файла, красный CI и несходящийся review. `plan` оценивает причину и задаёт переделку механизма или тестовой фикстуры. Редизайн выполняет тот же исполнитель, владеющий кодом и тестами. Повторные формулировки reviewer не считаются новым прогрессом.
- Если тест спорит с критерием, исполнитель проверяет текст задачи и исправляет тест в том же рабочем проходе. Недостающее продуктовое решение передаётся `plan` и владельцу.
- Источник состояния автоматической задачи — `activeTask` в `.ai-logs/agent-loop/state.json`. Reviewer не меняет stage-файл. Оркестратор объединяет возвраты к продукту и тестам в один пакет, принимает его узким review, затем делает один полный review всего локального diff. Владелец нужен только для задачи владельца, отсутствующего решения в документах, внешнего доступа или опасного действия.

## 1. Источник истины

| Вопрос | Где ответ |
| --- | --- |
| Что делает игра, формулы, числа | `docs/gdd/*.md`, числа — только `docs/gdd/10-balance.md` |
| Как выглядит | `docs/art/style-guide.md`, `docs/art/tokens.json` |
| Как устроен код | `docs/architecture/*.md`, `docs/architecture/adr/*` |
| Как тестировать | `docs/testing.md` |
| Git, комментарии, стиль кода | `docs/CONVENTIONS.md` |
| Что делать сейчас | текущий `docs/stages/stage-XX-*.md` |

- **Не выдумывай механики, числа, цвета, шрифты.** Если в доках нет ответа — остановись и запиши вопрос в `docs/QUESTIONS.md`, продолжай другие задачи.
- **Не меняй доки по своей инициативе.** Предложение → `docs/CHANGELOG-proposals.md` (что, почему, какие файлы затронет).
- **Прямое поручение владельца в чате** («поменяй X на Y») — разрешение менять доки. Порядок: доки → код → тесты → строка в `DECISIONS.md`, один коммит `change:`/`balance:`. Найди **все** упоминания изменяемого правила (grep по терминам и константам), а не только первое.
- Если поручение противоречит другим разделам доков — сначала перечисли конфликты владельцу, потом делай.
- Делай только объём текущего этапа. Порядок задач — строка «Очередь» в `STATUS.md`; найденный баг — в `docs/BUGS.md`, в текущей задаче чинится только Б1. Раздел «Вне объёма» в этапе — запрет, а не пожелание.

## 2. Стек (зафиксирован, см. ADR)

- TypeScript 5.x, `strict: true`, `noUncheckedIndexedAccess: true`, `exactOptionalPropertyTypes: true`.
- pnpm workspaces, Node 24 LTS.
- `packages/sim` — чистая симуляция, **ноль runtime-зависимостей**.
- `packages/protocol` — типы сообщений клиент/сервер, кодеки.
- `apps/server` — Node, `ws`.
- `apps/client` — Vite, PixiJS v8 (карта), React 19 (меню/HUD/карточки).
- Тесты: Vitest, fast-check, Playwright E2E для реальной браузерной геометрии и `pnpm probe:memory`.
- **Новые зависимости — только с записью в `docs/architecture/adr/`**. Запрещены: state-менеджеры (Redux, MobX, Zustand), ECS-библиотеки, UI-киты (MUI, shadcn, Chakra), CSS-фреймворки (Tailwind), lodash.

## 3. Железные правила симуляции (`packages/sim`)

1. Симуляция — функция `step(state, commands): state` (мутирующая внутри себя, но детерминированная). Тик = 100 мс (10 Гц).
2. **Только целые числа.** Все дробные величины — fixed-point: `FP = 1000` (1.0 = 1000). Деление только через `fpDiv`/`intDiv` из `packages/sim/src/math`. Запрещены `Math.random`, `Date`, `performance`, `Math.sin/cos/sqrt/pow` и любая float-арифметика с результатом, влияющим на состояние.
3. Порядок итераций стабилен: сущности хранятся в массивах, отсортированных по `id`. Никаких `for…in` по объектам, никаких `Set` с последующим порядкозависимым использованием.
4. `sim` не импортирует ничего из `server`, `client`, `protocol`, Node API, DOM.
5. Любая случайность (генерация карт, боты) — через seeded PRNG из `packages/sim/src/rng.ts`, сид передаётся явно.
6. Каждая механика реализуется **системой** — функцией в `packages/sim/src/systems/`, вызываемой из `step` в порядке, описанном в `docs/architecture/sim-core.md`.

Эти правила проверяются линтером (ESLint `no-restricted-globals`, `no-restricted-properties`) и dependency-cruiser. Не отключай правила через `eslint-disable` — это автоматический провал задачи.

## 4. Процесс работы над задачей

1. Прочитай задачу и критерии приёмки в этапе.
2. Прочитай соответствующие разделы GDD/арта/архитектуры (через `grep -n -C5`, по карте ниже).
3. Один исполнитель реализует продукт и тесты одного проверяемого механизма. Тест до проверки нового поведения подтверждает свою предпосылку: нужный объект, выбранное состояние и открытый экран. Reviewer проверяет общий diff; его замечания к коду и тестам исправляются одним пакетом.
4. Реализуй минимально достаточный код, который выполняет каждый критерий на реальном пути вызова; хардкод и обходной путь вместо механизма из задачи запрещены.
5. Исполнитель запускает целевые Vitest и Playwright `@layout`, затем `pnpm verify --changed` перед коммитом; цикл после коммита повторяет все тесты задачи и рабочий verify. Красный CI — задача не готова. Нельзя удалять или ослаблять чужие проверки ради зелёного результата. Неясный критерий фиксируется в `docs/QUESTIONS.md` и останавливает работу.
6. Коммит **по-русски** в формате `docs/CONVENTIONS.md`: `feat(sim): добавлена система сетей снабжения` + трейлер `Этап: 02/T7`. Рабочие роли могут создавать локальные атомарные коммиты; перед push оркестратор сводит историю задачи в один коммит.
7. Не меняй отметку задачи и STATUS: после зелёного CI это делает оркестратор.
8. Не push до финального review. Оркестратор push-ит проверенный HEAD и ждёт CI точного SHA.

## 5. Определение «готово»

- Все критерии приёмки задачи покрыты тестами и проходят.
- Оркестратор ставит `- [x]` только после финального `OK` reviewer и зелёного CI точного SHA. Пункт, который агент не может проверить, переносится в задачу владельца; он не считается автоматически принятым.
- `pnpm verify --changed` и CI зелёные, нет `any`, нет `// @ts-ignore`, нет `TODO` без ссылки на задачу.
- Публичные функции `sim` имеют JSDoc по-русски с единицами измерения (`/** @returns fixed-point, людей в секунду */`); комментарии — по правилам `docs/CONVENTIONS.md` §3.

## 6. Стиль кода (кратко; полностью — `docs/CONVENTIONS.md`)

- Коммиты, PR, комментарии, JSDoc, названия тестов — **по-русски**; идентификаторы и ветки — латиницей.
- Комментарий объясняет «почему», а не «что». Запрещены закомментированный код, «разговорные» комментарии, `TODO` без `(stage-XX/Tn)`.
- Функции ≤ 60 строк, файлы ≤ 400 строк. Больше — дроби.
- Именование: `camelCase` функции/переменные, `PascalCase` типы, `SCREAMING_SNAKE` константы баланса.
- Числа баланса — только из `packages/sim/src/balance.ts`, который 1:1 повторяет `docs/gdd/10-balance.md`. Магические числа в логике запрещены.
- Ошибки: в `sim` невалидная команда **отклоняется** (возврат `Rejected` с причиной), а не бросает исключение. На сервере — логирование + метрика, без падения комнаты.
- Никаких молчаливых `catch {}`.

## 7. Визуал — анти-«нейросетевые» правила (кратко, полностью в `docs/art/`)

Запрещено без явного разрешения в стайл-гайде:
- градиенты, glassmorphism, blur, неон, тени-свечения;
- шрифты Inter, Roboto, системные по умолчанию; эмодзи в UI;
- фиолетово-синие «tech» палитры, тёмный UI по умолчанию;
- скругления больше указанных в токенах;
- любые растровые картинки, сгенерированные нейросетью.

Все цвета — только из `docs/art/tokens.json`. Все размеры знаков армий — из `docs/art/units.md`.

## 8. Отчёт в конце этапа

Файл `docs/reports/stage-XX.md` (скилл `$stage-close`): что сделано по задачам, что отклонено/перенесено и почему, открытые вопросы, итог `pnpm verify`, известные риски.

## Команды проверки

| Команда | Что делает |
| --- | --- |
| `pnpm verify [--changed]` | **основная проверка**: build → типы → dependency-cruiser → lint → тесты; лог в `.ai-logs/verify-*.log`, в консоль итог ≤ 20 строк |
| `pnpm verify:prepush` | обязательный локальный gate оркестратора перед push: точный `pnpm check` из CI и все `@layout` E2E |
| `pnpm ai-check --changed` | быстрая проверка без build |
| `pnpm ai-check --staged` | lint staged-файлов (вызывает хук pre-commit) |
| `pnpm report:match --seeds N` | N матчей ботов, текстовая сводка метрик → `docs/reports/match/`, сводка ≤ 20 строк |
| `pnpm check` | быстрые проверки с подробным выводом — только workflow `ci` и составной `verify:prepush`, рабочей роли отдельно не запускать |
| `pnpm test:e2e:layout [файл]` | обязательные Playwright E2E с тегом `@layout` для реальной CSS-геометрии; запускаются автоматически в CI |
| `pnpm test:all` | все тесты с тяжёлыми `SLOW_TESTS` и покрытием (workflow `slow`) — только для CI, агенту не запускать |

Git-хуки (`.githooks/`, включает `pnpm install`): pre-commit — lint staged; commit-msg — заголовок ≤ 72, допустимые области, трейлер; pre-push — lint и commit-check ветки. Хуки агента (`.codex/hooks.json`): при завершении обычного ручного хода с грязным деревом запускается `pnpm verify --changed`; роли автоматического цикла освобождены от этого Stop-хука, их проверки выполняет оркестратор; ручной `pnpm dev`, ручной браузер и остановка процессов блокируются. `gh` не установлен: CI — через REST API GitHub (curl), скилл `$ci`.

## Правила работы (экономия токенов)

- Поиск: сначала `rg -l` только для имён файлов, затем `rg -n -C2` по 1–2 файлам с `| Select-Object -First 80`.
- Большая задача — `$split`; приёмочные матчи — `$accept` отдельной сессией после коммита.
- **Рабочая проверка — целевые тесты задачи и `pnpm verify --changed`** (в работе и перед коммитом). Для UI-геометрии разрешён автоматический `pnpm test:e2e:layout <файл>`. Полный `pnpm verify` — в `$stage-close`, тяжёлые тесты — в CI. Детали ошибок читай в `.ai-logs/<лог>` без повторного полного прогона.
- Длинные команды — на переднем плане с `timeout`; без фоновых задач и опроса.
- Не останавливай процессы (`Stop-Process`, `taskkill`, `kill`): рядом работают агентный цикл и другие сессии. Зависшую свою команду обрывает её таймаут.
- **Ручной браузер, картинки и видео запрещены.** Автоматический `pnpm test:e2e:layout` разрешён для измеримой CSS-геометрии; автоматический `pnpm test:e2e:visual` и один вызов `$review` на готовые снимки разрешён как визуальный гейт перед push (см. §0) — рабочим ролям самим смотреть на картинки или открывать браузер всё равно запрещено. Субъективный вид дополнительно проверяет владелец по ссылке предпросмотра ветки в раундах 07/T17.
- Независимые команды объединять в один вызов.
- Читать через `grep -n` с контекстом; файл целиком — только тот, что правишь. Исключение: блок своей задачи этапа и блок её родителя читаются целиком.
- Многострочный текст (коммит, отчёт, файл) — через временный файл, не heredoc.
- Дизайн-вопросы — одним списком и остановиться; код до ответа не начинать.
- Отчёт в чате — до 10 строк со ссылкой на `docs/reports/`; все ответы владельцу — по-русски.
- Сгенерированные файлы токенов (`apps/client/src/theme/tokens.*`) не форматировать prettier — `pnpm tokens`.
- Одна активная задача. Рабочие сессии создают локальные атомарные коммиты; `STATUS.md`, push и ожидание CI выполняет оркестратор.
- Бюджет одной задачи рассчитан на самую дешёвую модель цикла: один проверяемый механизм со всеми необходимыми файлами продукта и тестов. `plan` разбивает задачу по независимым механизмам, а не по числу файлов. Повторный дефект той же причины требует пересмотреть подход или фикстуру; число коммитов само по себе не доказывает прогресс.
