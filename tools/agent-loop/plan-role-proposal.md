# Предложение: роль `plan` — приём сырых задач от владельца

**Статус:** предложение, не реализовано · 2026-10-17

## Проблема

Сейчас владелец либо пишет задачу в точном формате команд цикла (`$task`, `$decide`, `$split`…),
либо получает её от AI-сессии, которая сама превращает его слова в точный текст Issue (пути
файлов, приёмку, разбиение на подзадачи). Без такой сессии посередине:

- владелец не может быстро накидать Issue своими словами и доверить её исполнителю;
- исполнитель (`$task`/`$next`), получив расплывчатую или слишком большую задачу, либо
  останавливается с вопросом в середине работы (дорого — уже потрачен круг), либо, хуже,
  додумывает объём сам и уходит не туда (07/T22, 2026-10-17: задача «почини красный CI» без
  названных файлов — исполнитель заодно отредактировал код самого цикла).

Решает это не сторож (это уже сделано кодом — `scope-guard.ts`, `return-guard.ts`), а проверка
**до** начала работы: правильные ли файлы, один объём или несколько, есть ли вообще ответ в
доках.

## Предлагаемое решение

Новая роль `plan`, аналогичная по месту в пайплайне `spec`: отдельная модель/промпт, узкие права,
результат — не код, а точный текст задачи в файле этапа или вопрос в `docs/QUESTIONS.md`.

### Поток

1. Владелец создаёт Issue с меткой `agent`, первая строка — `$plan`, дальше — текст своими
   словами, без формата.
2. Цикл запускает сессию `plan` с этим текстом вместо прямого `$task`/`$decide`.
3. Сессия `plan`:
   - находит файлы, которых касается просьба (`rg -l`), проверяет, что они существуют;
   - читает нужные разделы доков по таблице `AGENTS.md` «механика → раздел GDD»;
   - решает: **один** объём или несколько — критерий размера как у `$split` («Файлы:», «После:»
     в тексте задачи), только автоматически, без ожидания просьбы исполнителя;
   - если в доках нет ответа на дизайн-вопрос — не придумывает, а пишет вопрос в
     `docs/QUESTIONS.md`, Issue после коммита закрывается штатно, работа не начинается;
   - если всё ясно — пишет блок(и) задачи в `docs/stages/stage-NN-*.md` в формате, который понимает
     `$next`/`$task` (как делает `$split`), и добавляет их в «Очередь» `docs/STATUS.md`.
4. Дальше задача идёт по обычному циклу `$next` → CI → `$review`.

### Права (`permissions.json`)

```json
"plan": ["docs/stages/**", "docs/STATUS.md", "docs/QUESTIONS.md", ".ai-logs/**"]
```

Та же идея, что у `reviewer`: роль `plan` не трогает код продукта и не трогает
`tools/agent-loop/**` — значит, повторить 07/T22 (правка собственного кода цикла) она физически
не может.

### Модель/усилие (`roles.json`)

Такая же модель, что у `next`/`review`/`spec` (сейчас `gpt-5.6-luna`, `reasoningEffort: medium`) —
задача требует понимания доков и оценки объёма, не формальность.

### Провод в цикле

- Новый скилл `.agents/skills/plan/SKILL.md` — шаги по аналогии с `$split`/`$decide`.
- `issues.ts`: Issue с первой строкой `$plan` (как уже разобраны `$task`, `$decide`, `$bug`…) идёт
  в сессию `plan`, а не в `next`/`task`.
- Тесты — как у `review-scope.ts`/`scope-guard.ts`: разбор текста Issue, проверка существования
  файлов, формирование блока задачи, случай «нет ответа в доках → вопрос, работа не начата».

## Что это НЕ решает

- Не ловит нарушения **внутри** работы исполнителя (переписанный без объяснения тест, пропуск
  пункта возврата) — это по-прежнему держат `scope-guard.ts`, `return-guard.ts` и `$review`.
- Не снимает обязанность исполнителя останавливаться на дизайн-вопросе (`AGENTS.md` §4, шаг 4) —
  `plan` снимает часть таких вопросов заранее, не все.

## Объём работы

По порядку `scope-guard.ts` (модуль + провод + тесты) — один рабочий круг с проверкой CI.
Собственно `plan`-роль крупнее: новый скилл с полным текстом (аналог `$split`/`$decide` по
объёму), провод в `issues.ts`, тесты на разбор свободного текста. Ориентир — 2–3 часа работы с
циклами CI, то есть задача для отдельной сессии, не хвост к текущей.

## Открытые вопросы владельцу

1. Что делает `plan`, если присланный текст уже достаточно точен (готовая задача владельца в
   понятном формате) — пропускает сразу в очередь или всё равно формализует блок задачи?
2. Если `plan` решил разбить на несколько задач — нужно ли подтверждение владельца перед тем, как
   они уйдут в очередь, или достаточно записи в `docs/DECISIONS.md` постфактум (как делает
   `$split` сейчас)?
3. Нужна ли `plan`-роли сверка с `docs/BUGS.md` (не дублирует ли просьба уже открытый баг)?
