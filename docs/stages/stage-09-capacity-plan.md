# План: сотня онлайна на самом слабом сервере и слабый клиент

**Цель (владелец, 2026-11-11):** мультиплеер работает на клиенте самой слабой железяки; сервер 1 vCPU / 512 МБ держит около 100 человек онлайна; геймплей не урезается (боты не «думают меньше»).

## Что показали замеры

Настоящие сокеты, сервер — отдельный процесс с теми же лимитами V8, что на VPS (`tools/bench/src/ws-load.ts`):

| Сценарий | Тик хаба p50 / p99 / макс | Процессор | Память |
| --- | --- | --- | --- |
| 8 комнат × 3 человека (разреженные, остальное боты) | 58 / 86 / 207 мс | 81% ядра | 145 МБ |
| 4 комнаты × 25 человек (100 онлайна, комнаты упакованы) | 28 / 40 / 219 мс | 45% ядра | 129 МБ |

Выводы:

1. **100 онлайна на одном ядре уже помещается, если комнаты упакованы людьми** (≈ 7 мс на комнату, 4 комнаты). «Впритык» — это разреженные комнаты: 3 человека + 27 ботов стоят столько же, сколько 25 человек + 5 ботов, то есть цена комнаты почти не зависит от числа людей.
2. **Максимум 207–219 мс — это создание комнаты** (генерация карты и `createMatch` прямо в тике хаба): все игроки всех комнат на этот момент замирают. Это главный дефект.
3. Поздняя игра дороже: ×1,3–1,4 к раннему тику (ботов 5,5 → 7,4 мс за 10 минут), значит 4 комнаты — ≈ 40 мс, запас до 100 мс уже небольшой.
4. Лимит комнат статический (6): он не знает ни реальной цены тика, ни числа людей.
5. Полный снимок — 88 КБ, после deflate 3 КБ; поток вида 4–5,4 КБ/с на игрока (≈ 15–19 МБ в час мобильного трафика).
6. Онлайн-клиент не считает симуляцию вообще (она на сервере): он дешевле локальной игры. Это нужно измерить зондом, а не предполагать.

## Рабочие пакеты (по порядку, у каждого есть критерий)

**П1. Убрать провалы тика.** Карты матча грузятся из готовых файлов (20 сидов), а не генерируются; создание матча уходит из тика хаба (заготовленная комната в запасе или нарезка на куски между тиками). Критерий: макс тика хаба при создании комнаты ≤ 60 мс (`ws-load`).

**П2. Упаковка комнат и допуск по цене.** Открытая комната заполняется людьми в первую очередь (самая заполненная с местом, а не первая); вместо `MAX_ROOMS` хаб считает скользящую цену комнат (мс на тик) и пускает новую комнату, только если прогноз суммы ≤ 65 мс; иначе игрок видит очередь «сервер занят, место N» — идущие матчи не деградируют. Размер закрытой комнаты выбирает хозяин (10 / 20 / 30 мест): меньше мест — дешевле, это продуктовое решение владельца, а не урезание ботов. Критерий: 100 онлайна из разных сценариев входа (одиночки, группы, все вперемешку) укладываются в p99 ≤ 60 мс на 10-й минуте матча.

**П3. Дешевле тик сервера без потери геймплея.** Профиль под нагрузкой (`--cpu-prof` на `ws-load`): шаг sim, `playerView` на человека, кодирование JSON, отправка. Кандидаты: журнал изменений вместо сравнения слоёв (`buildViewDelta` за O(изменений)), общий кэш кодирования для неизменных частей, накопительный `viewAck` раз в 2 вида (вдвое меньше входящих), кэши ботов (`incomeBases`, поиск пути, снабжение). Критерий: −25–30% к цене комнаты на 10-й минуте, все golden-тесты и детерминизм без изменений.

**П4. Несколько ядер.** *Сделано (ADR-0018): шлюз в I/O-потоке и пул шардов-воркеров, каждый ведёт много комнат; размещение по цене.* Комнаты уезжают в `worker_threads` (ADR-0017, п. 7): главный поток держит только сокеты и маршрутизацию, воркеры — комнаты; число воркеров = число ядер (на 1 vCPU — один воркер, накладные расходы замерить). Критерий: на 4 ядрах ≈ 4× комнат при том же p99; перегруз одной комнаты не задерживает остальные воркеры.

**П5. Слабый клиент.** Зонд телефона (Playwright, CPU ×4/×6) против локального сервера: бюджеты на приём одного вида (разбор + применение + рендер), память, первый снимок. Если приём заметен на ×6 — разбор и применение дельт переезжают в Web Worker (по образцу локального режима), главный поток только рисует. Критерий: ≥ 55 кадров/с на ×6 в онлайн-матче 30 игроков, приём ≤ 4 мс на вид при ×6.

**П6. Трафик.** Замерить `permessage-deflate` (CPU сервера и экономию) и компактный бинарный кодек для колонок гексов; выбрать по цифрам. Критерий: ≤ 2 КБ/с на игрока (≈ 7 МБ/час), рост CPU сервера ≤ 5%.

**П7. Надёжность под нагрузкой.** Хаос-тест на 30 клиентах (обрывы, потери, всплески пинга), штурм реконнектов, часовой замер памяти без утечек, дренаж при выкладке (сервер перестаёт брать новые комнаты и ждёт конца идущих, чтобы деплой не убивал матчи).

**П8. Эксплуатация.** Выкладка из GitHub Actions по ключу (секреты агенту не видны), отдельный пользователь `deploy` с правом только перезапустить сервис, swap/zram 1 ГБ на 512 МБ, `/healthz` и строка метрик раз в минуту, откат.

## Целевые цифры

| Показатель | Сейчас | Цель |
| --- | --- | --- |
| Онлайн на 1 vCPU / 512 МБ | ~100 при упакованных комнатах, ~24 при разреженных | 100 при любом составе |
| Макс. тика хаба | 207–219 мс | ≤ 60 мс |
| p99 тика на 10-й минуте при 100 онлайна | ~40 мс (ранняя игра) | ≤ 60 мс |
| Трафик на игрока | 4–5,4 КБ/с | ≤ 2 КБ/с |
| Кадры в онлайне, CPU ×6 | не измерено | ≥ 55 |
| Ядер → онлайна | 1 → ~100 | 4 → ~400 |

## Вне плана

Бот не «думает меньше», радиус и частота командования не снижаются; бинарный кодек и воркеры вводятся только по цифрам замеров.
