# Лаги онлайн-матча при больших армиях: диагностика и исправления

Этап 09/T17. Жалоба владельца: у каждой стороны ≈200 отрядов, в сумме 100к+ солдат — зум и приказы идут с задержкой.

## Сценарий нагрузки

`net-bench.ts` получил опции `--armies=N --soldiers=S --armies-at=M`: на минуте M каждому живому игроку добавляется N отрядов по S солдат (стек на его гексах), дальше матч идёт как обычно (боты командуют новыми отрядами). Также в бенч добавлена клиентская сторона первого человека: разбор JSON и `ViewDeltaApplier.applyDelta` (`кл:разбор`, `кл:применение`, в итог сервера не входят).

Запуск (30 игроков, карта gen, medium, туман, 6000 отрядов по 25 солдат = 150 тыс. солдат, 5 минут):

```
node --max-semi-space-size=2 --max-old-space-size=256 --expose-gc --experimental-strip-types tools/bench/src/net-bench.ts --humans=30 --armies=200 --soldiers=25 --armies-at=1 --minutes=5
```

Цифры — мой ПК, мс на тик (бюджет комнаты ≤ 40 из 100; тик > 100 мс = сервер не успевает, приказы и картинка отстают).

## Что нашёл

Профиль (`--cpu-prof`) до правок: тик в минуте 2 (война 6000 отрядов) — **260 мс, из них виды игроков 170 мс**. Причина — квадратичный обход в `playerView`: для каждого отряда с приказом `attack` считалась оценка боя (`attackState`): полный обход всех отрядов матча, `unitViews` противника целиком на каждый вражеский отряд, `forecastBattle` с копированием всех отрядов (`fighter`) и `includes` по списку приказа. Для 200 отрядов, бьющих в один гекс, — 200 одинаковых прогнозов на каждого из игроков каждый тик.

## Что исправлено

| Правка | Файлы |
| --- | --- |
| Оценка боя считается один раз на пару (владелец, цель), а не на отряд; «всевидящий» вид владельца для чужих атак — один на тик в `PlayerViewContext.omniUnits` | `queries/player-view.ts` |
| `forecastBattle`: множество вместо `includes`, без копирования всех отрядов; `isSupportedByArtillery` — `hexDistanceById` без выделений | `queries/forecast.ts`, `queries/battle-math.ts` |
| `routePath`: прогноз «слабый враг» кэшируется по гексу на время одного поиска; `forecastInState` берёт защитников из индекса отрядов по гексу | `commands/unit.ts`, `queries/forecast.ts` |
| `procure`: сила армий одним проходом, а не в компараторе сортировки (O(армии·log·отряды)) | `systems/procure.ts` |
| Зона контроля: война с владельцем — один массив, а не вопрос дипломатии на отряд; `nearLine` (линия наступления) без объектов `Hex` | `queries/unit-path.ts`, `state/offensive-steps.ts` |

Результат симуляции не менялся: те же числа отрядов минута за минутой, 692 теста sim зелёные, golden без изменений.

## Чего не удалось / не сделано

- **Рендер Pixi, React, обработка кликов в браузере не измерены.** Ручной браузер запрещён, а зонд `apps/client/tests/probe` работает на локальной игре, а не на онлайн-матче с вброшенными армиями. Узкое место «зум/приказ тормозят» в браузере остаётся гипотезой: сервер при 100–260 мс на тик отдавал картинку редко, что даёт ощущение запаздывания, но подтвердить на клиенте нечем. Следующий шаг — зонд в режиме `online` против сервера с вбросом армий.
- Тик всё ещё > 40 мс бюджета на 30 людях в бою (51–59 мс), главный остаток: виды + `buildViewDelta` (≈ 23 мс на 30 людей), боты (≈ 13 мс), `step` (≈ 15–18 мс). При 3 людях бюджет выдерживается.
- Всплеск на старте войны (≈ 100 мс) — часть искусственна: 6000 отрядов вбрасываются сразу.
- Трафик дельты в бою выше бюджета; кандидат — не слать `path` и поля, которые клиент выводит сам, и объединять патчи отрядов одного приказа.
- Следующие структурные кандидаты: кэш `planViews` по версии плана (одинаков между тиками, пока нет боёв на фронте), журнал изменений вместо diff вида с видом.
