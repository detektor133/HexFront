# Протокол клиент ↔ сервер

Транспорт: WebSocket (`wss://`), один сокет на игрока. Версия протокола в `packages/protocol/src/version.ts`, несовпадение → сервер отвечает `versionMismatch` и закрывает.

## Кодек

- Этап 06: JSON (простота отладки). Метрика трафика на игрока логируется.
- Если средний трафик > 4 КБ/с на игрока — переход на бинарный кодек (свой, на `DataView`, без зависимостей) через ADR.

## Клиент → сервер

```ts
type C2S =
  | { t: 'hello'; v: number; nick: string; token?: string; room?: string; mode?: 'open' | 'private' }
  | { t: 'cmd'; seq: number; cmd: Command }          // seq — для подтверждений
  | { t: 'viewAck'; tick: number }                    // подтверждение применённого снимка или дельты
  | { t: 'ping'; at: number }
  | { t: 'start' };                                   // хозяин закрытой комнаты запускает матч
```

Кодек и проверки — `packages/protocol/src/messages.ts`. Вход: `mode: 'open'` (по умолчанию) — комната «Играть онлайн», сбор 30 с, свободные места занимают боты; `mode: 'private'` создаёт закрытую комнату, её код приходит в `welcome.room`, друзья входят с `room`; `token` возвращает игрока на прежнее место (реконнект).

Команды — `Command` из `sim` (`architecture/sim-core.md`), в том числе `setArmyAuto` и `setAutoCommand` (CR-006). Сервер принимает только известные типы с простыми полями (целые, булевы, строки до 40 символов, массивы до 512), сообщение больше 8 КБ отбрасывается; `source: 'auto'` клиент не отправляет — его ставит только сервер для команд commander.

Rate limit: ≤ 20 команд/с на игрока; превышение — команды отбрасываются с `rejected: rateLimit`.

## Сервер → клиент

```ts
type S2C =
  | { t: 'welcome'; playerId: number; token: string; room: string; tickMs: number;
      map: string; seed: number; players: number; fog: boolean }    // карту клиент собирает по map+seed
  | { t: 'lobby'; info: { room; humans; max; startsInS: number | null; open: boolean } }
  | { t: 'start'; tick: number }
  | { t: 'snapshot'; tick: number; view: PlayerViewFull }        // при входе/реконнекте
  | { t: 'delta'; tick: number; baseTick: number; d: ViewDelta }   // после подтверждения baseTick
  | { t: 'ack'; seq: number } | { t: 'rejected'; seq: number; reason: string }
  | { t: 'refused'; reason: 'versionMismatch' | 'badNick' | 'roomFull' | 'noRoom' | 'badHello' }
  | { t: 'end'; winner: number; tick: number }
  | { t: 'pong'; at: number };
```

События для ленты едут внутри `delta.d.events`; игроку уходят только его события и политические (захват города, выбывание, победа, дипломатия с его участием). Поток дельт один на клиент и сервер (`ConfirmedViewDeltaStream` в `packages/protocol`, ADR-0017).

## Дельта-снимки

`ViewDelta` содержит только изменившиеся гексы, отряды, фронты и события относительно последнего подтверждённого снимка. Клиент подтверждает применённый снимок сообщением `viewAck`; сервер и локальный воркер не используют неподтверждённый снимок как базу следующей дельты.

Форма дельты (`d`): `hexes` — слои гексов колонками «зазор по id, значение»; `keyed` — коллекции с id патчами (`add`, `patch`, `removed`); `records` — патчи записи `me`; `whole` — остальные изменившиеся поля вида целиком; `unset` — исчезнувшие необязательные поля; `events`. Формат выводится из структуры `PlayerView`, медленные поля (население, экономика) обновляются раз в секунду. Принципы, бюджеты и тесты-предохранители — в `performance.md`. Замер (30 ботов, 30 людей, туман): дельта 8,7 КБ → 0,9 КБ за тик на игрока (≈ 3,5 КБ/с после deflate).

Полный снимок обязателен при старте, реконнекте, смене вида наблюдателя и смене режима тумана. После полного снимка его `tick` становится новой базой дельт.

Этот формат используется локальным воркером и является основой серверного протокола этапа 09.

## Туман на сервере

- `ViewDelta` строится из `playerView` игрока: сервер хранит последний подтверждённый вид и шлёт разницу.
- Сервер строит `playerView` отдельно для каждого игрока; общий снимок между игроками не используется, потому что зоны обзора и память тумана различаются.
- Бюджет построения и сериализации снимка измеряется отдельно от `step` и ботов; оптимизация этого бюджета относится к отдельной задаче этапа сервера.
- Параметр матча `fog` передаётся в снимке состояния; при `fog: false` сервер отдаёт полный `playerView` и не формирует `forget` для тумана.
- Изменения владельцев гексов и городов — всем (политическая карта видна всегда).
- Армии, дороги, постройки — только внутри зоны обзора; при выходе из обзора — `forget`-сообщение с последним известным состоянием для «памяти».
- Прогноз боя на клиенте считается по `PlayerView` — клиент не знает больше, чем видит.

## Реконнект

- Токен сессии в `welcome`; при обрыве клиент переподключается с тем же токеном в течение 30 с → `snapshot`, управление возвращается.
- Через 30 с без соединения отряды и армии игрока переходят боту (`08-match.md`).

## Интерполяция на клиенте

Клиент рендерит с задержкой 100 мс и интерполирует позиции отрядов между тиками по прогрессу перехода (прогресс — часть `ViewDelta`).

## Надёжность связи (восстановление после потерь)

WebSocket надёжен и упорядочен, пока жив TCP; потери возникают при обрывах, смене сети и «тихой» смерти канала. Поэтому протокол устроен как возобновляемая сессия:

- **Команды идемпотентны.** Клиент нумерует команды (`seq` растёт в сессии) и хранит до `ack`. `ack` накопительный. После обрыва неподтверждённые уходят заново в том же порядке; сервер помнит последний исполненный `seq` и повтор не исполняет, а только подтверждает.
- **Возобновление вида.** В `hello` реконнекта клиент называет `have` — тик последнего применённого вида. Если сервер помнит эту базу (последнее подтверждённое или отправленное сообщение), поток продолжается дельтами без полного снимка. События неподтверждённого сообщения возвращаются в очередь и не теряются; события за время обрыва копятся (до 256).
- **Наблюдение выбывшего.** `watch {player}` переключает вид на другого игрока: сервер шлёт полный снимок его вида, карточки и прогнозы считает для него, команды из такого вида отклоняет (`rejected: bad`). Живому игроку `watch` молча игнорируется.
- **Нет базы — полный снимок.** Любая рассинхронизация (ошибка применения, битое сообщение, потерянный `viewAck` дольше 10 с) заканчивается `resync` или полным снимком, а не перезапуском матча.
- **Мёртвый канал.** Клиент шлёт ping каждые 2 с и сам разрывает соединение без входящих 6 с; сервер пингует ws каждые 10 с и обрывает не ответивших. Место игрока держится 30 с, затем армиями занимается бот; возврат по токену отдаёт управление обратно.
- **Повторы подключения** — экспоненциально от 250 мс до 5 с с разбросом, чтобы массовый обрыв не стал волной; клиент сдаётся через 5 минут.
- **Высокий пинг.** Окно отправки — до 12 сообщений вида без подтверждения: следующая дельта строится от последнего отправленного вида (канал упорядочен), а не от подтверждённого, поэтому вид идёт на каждом тике и при круговой задержке 600 мс (тест `net-e2e`: > 250 видов за 40 с). Окно заполнено 10 с без `viewAck` — полный снимок. Экран игры показывает вид с задержкой 100 мс (ровный шаг при разбросе сети) и применяет все сообщения очереди по порядку.
- **Расчёты по полному состоянию.** У клиента сети нет `MatchState`, поэтому карточка гекса (`select` → `selection`), прогноз пути и маски карты (`query` → `pathPreview`/`mapMask`) считаются на сервере для игрока. Карточка уходит только для видимого гекса и только при изменении; запросов не больше 30 в секунду; маска сжимается повторами.

## Защита от читов и злоупотреблений

Сервер авторитетен: клиент шлёт только намерения, состояние и вид строит сервер.

- Форма сообщения и команды проверяется до sim (`messages.ts`): белый список типов, простые поля ограниченного размера, `source` запрещён; смысл команды (чей отряд, хватает ли золота) проверяет sim, чужой отряд отклоняется как `commandRejected`.
- Команды берут `playerId` из места на сервере; клиент не может написать за другого игрока.
- Лимиты: 20 команд/с и 64 в очереди тика на игрока, 100 сообщений/с на соединение (флуд — разрыв), 8 КБ на сообщение, 10 соединений и 30 `hello` в минуту на адрес (подбор токенов и кодов комнат упирается в лимит), `hello` в течение 5 с, не больше 8–12 комнат на процесс (`busy`).
- Токен сессии — 144 бита случайности (`randomBytes`), клиент получает его только в `welcome`.
- Туман: чужие отряды вне обзора, чужая казна и налог в вид не попадают; события — только свои и политические.
- Проверка `Origin` (список и шаблоны `https://*.example.com`) закрывает чужие сайты; адрес клиента за Caddy берётся из `X-Forwarded-For` только при `TRUST_PROXY=1`.
- Соединение с очередью отправки больше 4 МБ обрывается как медленное.
