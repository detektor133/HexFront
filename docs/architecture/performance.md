# Производительность и трафик: принципы и бюджеты

Документ фиксирует правила, по которым сервер и клиент укладываются в бюджет на дешёвом VPS, и то, как не сломать их при добавлении механик. Цифры — замеры `node --expose-gc --experimental-strip-types tools/bench/src/net-bench.ts 30 18000` (30 ботов, **все 30 — люди**, то есть худший случай; туман, seed 43, 30 минут матча на ускорении; быстрый вариант — `pnpm --filter @hexfront/bench net`).

## Бюджеты

| Что | Бюджет | Замер 2026-11-10 (мин 1 → мин 30) |
| --- | --- | --- |
| Тик комнаты (боты + `step` + виды + дельты + JSON) на 30 людей | ≤ 40 мс из 100 | 17 → 27,5 мс |
| Трафик дельты на игрока | ≤ 4 КБ/с после deflate | 3,4 → 3,2 КБ/с (≈ 9–19 КБ/с без сжатия) |
| Куча Node (после GC) | без роста | 14 → 16 МБ (утечки нет) |

Тик растёт к поздней игре вместе с числом отрядов (193 → 547 на 30-й минуте); это не утечка, а честная стоимость боёв. Выросли цифры — это дефект, а не «потом оптимизируем»: прогоните бенч до и после своей правки.

## Принципы протокола вида (`packages/protocol/src/view-delta.ts`)

1. **Формат выводится из структуры `PlayerView`, а не из списка полей.** Новое поле вида доезжает до клиента само (целиком при изменении). Регистрировать его нигде не нужно.
2. **Безопасно по умолчанию.** Каждое поле едет каждый тик. Замедлить поле можно только явным внесением в `SLOW_*` (`paceView`): медленные поля обновляются раз в `SLOW_PERIOD_TICKS` = 10 тиков. Добавить поле так, чтобы оно тихо запаздывало, нельзя.
3. **Патчи по ключу.** Коллекции с `id` (отряды, города, игроки, рейтинг, армии, стройки, наборы, планы по `armyId`) передаются как `add` (запись целиком), `patch` (только изменившиеся поля) и `removed`. Новая коллекция с id добавляется одной строкой в `KEYED` и обязана быть отсортирована по ключу.
4. **Слои гексов — колонками** «зазор по id, значение». Новый слой гексов подхватывается сам.
5. **База дельты — вид, каким он оказался у клиента** (`paceView`), а не сырой вид сервера. Иначе пропущенные медленные изменения не дойдут никогда.
6. **Скрытое не уходит.** Чужая казна и налоги в `playerView` всегда 0.

## Тесты-предохранители

- `tools/replay/src/view-delta-roundtrip.test.ts` — реальный матч 30 ботов, два наблюдаемых игрока, туман и без, дельта через настоящий JSON обязана восстановить вид побитово. Тест не знает полей вида: сломается любая ошибка схемы, а новое поле он проверит само. Между синхронизациями отстать могут только поля из `SLOW_*`.
- Добавили поле в вид и тест красный — чините схему передачи, а не тест.

## Правила горячего кода (`packages/sim`, `packages/protocol`)

Профиль показал: время уходило не на «медленный язык», а на мелочи в циклах по тысячам гексов. Поэтому:

- В циклах по гексам/отрядам — обычный `for` по индексу. Не использовать `TypedArray.from(src, fn)`, `forEach`/`map` с замыканием по всей карте, `Object.keys` и создание объекта на каждый гекс.
- Копии слоёв для вида — `slice()` (memcpy) или явный цикл; общие данные на тик (`createPlayerViewContext`) считаются **один раз** и передаются во все `playerView` комнаты.
- Не пересобирать то, что не изменилось: неизменный слой — та же ссылка (`before === after` пропускает сравнение), сравнение по 4 байта.
- Перед «оптимизацией» — профиль (`node --cpu-prof`), после — замер `net` и запись цифр сюда. WebAssembly оправдан только если профиль показывает одну доминирующую функцию; сейчас профиль плоский (самая тяжёлая строка ≈ 6%).

## Следующие шаги, если бюджет снова упрётся

1. Журнал изменений в симуляции (какие гексы/отряды изменились за тик) вместо сравнения вида с видом: стоимость дельты пропорциональна числу изменений, а не размеру карты.
2. Кэш слоёв вида по версиям слоя в `state`, чтобы не копировать неизменные слои каждому игроку.
3. Бинарный кодек (`DataView`) поверх тех же патчей, если deflate на сервере окажется дороже.
