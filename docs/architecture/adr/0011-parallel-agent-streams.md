# ADR 0011: Параллельные потоки агентного цикла

## Решение

Цикл ведёт до N задач этапа одновременно, N от 1 до 4 задаёт Issue `$streams N` или `pnpm agent:run --streams N`; значение запоминается в памяти цикла и читается на каждом шаге. По умолчанию 1 — прежний цикл по одной задаче в главном каталоге. Смена режима — в свободной точке: 1 → N, когда в главном каталоге нет незакоммиченной работы; N → 1 — новые задачи потокам не выдаются, начатые доделываются, после этого цикл возвращается в главный каталог. Больше 4 не даёт выигрыша: упор в общие файлы, зависимости задач и лимит codex.

**Поток** — постоянный `git worktree` рядом с репозиторием (`<репозиторий>-streams/wN`, короткий путь из-за предела путей Windows) и своя ветка `agent/NN-Tn` на задачу. В потоке идёт прежняя цепочка `$spec` → `$task NN/Tn` → CI → `$review`. Сессии потока получают строку «Поток wN: ветка agent/NN-Tn …»: скиллы сверяют ветку с ней и не меняют `docs/STATUS.md`. У каждого потока свой порт visual (`VISUAL_PORT`), своя память `.ai-logs/agent-loop/state.json` в каталоге потока; протокол — один, в главном каталоге, строки с префиксом `[wN NN/Tn]`.

**Выбор задач** делает цикл, а не `$next`: первая задача «Очереди» `[ ]`, не задача владельца, чьи зависимости закрыты и чьи файлы не пересекаются с задачами в работе. Зависимости и файлы — строки блока задачи `*После:*` и `*Файлы:*`, их пишет `$decide`. Без `После:` задача ждёт все задачи перед ней в очереди, без `Файлы:` — пересекается со всеми: неразмеченный этап идёт по одной задаче, как раньше. Задача владельца держит только задачи, которые от неё зависят.

**Слияние** — очередь по одной задаче, ветка этапа всегда зелёная (merge queue, «not rocket science rule»): после `$review` OK свежая ветка этапа вливается в ветку задачи, CI проверяет слитое дерево, ветка этапа сдвигается fast-forward. Ушла вперёд — слить снова. Конфликт — сессия `$task NN/Tn слияние`, затем повторный `$review`. Повторный `$review` и без конфликта, если ветка этапа за время задачи меняла те же рабочие файлы (смысловой конфликт) или задача меняла файлы вне своего `Файлы:`. Служебные docs (отметки этапа, отчёт, BUGS, DECISIONS, QUESTIONS) в эти проверки не входят; дописываемые файлы сливаются драйвером `merge=union` (`.gitattributes`). Ветка этапа меняется только под общим замком главного каталога: Issues, исправление `slow` и fast-forward не идут одновременно.

**Отмена:** Issue, изменившая блок задачи в работе, отменяет поток при следующей сессии; работа отбрасывается, задача начинается заново по новому тексту. **Перезапуск** цикла продолжает задачи потоков по веткам `agent/*` их каталогов. `$stage-close` — только когда все потоки свободны.

## Почему

Задача этапа — это в основном время сессий codex (этап 06: в среднем ~22 мин от начала до `[x]`), поэтому параллель сокращает всё время задачи, а не только проверки. Расписание этапа 07 по его зависимостям и общим файлам даёт ×1,2–1,3 при двух потоках (моделирование, не замер); этапы с независимыми задачами выигрывают больше. Число потоков ограничивает лимит Codex: токенов на задачу столько же, тратятся они в N раз быстрее.

## Отклонено

- Агенты сами договариваются, кто что берёт: порядок задаёт владелец «Очередью».
- Слияние без CI на слитом дереве: чистое текстовое слияние не доказывает, что код работает.
- Пакетные спекулятивные слияния: при 2–3 потоках выигрыша нет, а красный пакет требует поиска виновника.

## Проверка

`tools/agent-loop/src/streams.test.ts` — сценарии на настоящем git (origin, worktree, ветки, слияния, конфликты), поддельные только codex, CI и GitHub: одновременная работа, пересечение по файлам, `После:`, конфликт, смысловой конфликт, красный CI в одном потоке, `ВОЗВРАТ`, `$decide` посреди работы, задача владельца, обрыв и перезапуск, работа владельца в главном каталоге, закрытие этапа, `$streams 2` и `$streams 1` на ходу. `tools/agent-loop/src/scope.test.ts` — выбор задач.
