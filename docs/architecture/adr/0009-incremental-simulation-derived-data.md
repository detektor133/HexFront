# ADR-0009: Инкрементальные производные данные симуляции

**Статус:** принято · 2026-10-06

## Контекст

`visionSystem`, `lossMap`, `lossFrom` и `recomputeNetworks` выполняют работу по всей карте отдельно
для игроков или сетей. При росте числа игроков это увеличивает стоимость одного тика быстрее,
чем растёт число игроков. Боты повторно запрашивают те же производные данные.

## Решение

1. Внутри тика запрещены проходы по всей карте для каждого игрока.
2. `vision` и `networks` остаются в `MatchState` и стабильном хэше. Они обновляются инкрементально
   при смене владельца гекса, движении отряда, постройке и изменении дороги.
3. Карты потерь снабжения, изолированные гексы, виды ботов и общие расчёты тика хранятся в чистых
   кэшах вне `MatchState` и не влияют на хэш.
4. `incomeBases` и `growthPerSecond` считаются одним проходом по карте не более одного раза за тик
   и переиспользуются `step` и ботами.
5. Частота обновления обзора остаётся `VISION_RECALC_TICKS`; меняется только способ обновления.
   Полный пересчёт допускается при создании матча и в тестах эквивалентности.

## Приёмка

- T14a–T14d сравнивают инкрементальные результаты с полным пересчётом на нескольких тысячах тиков.
- Golden-хэши не меняются.
- На минутах 1–5 матча Node 22 `step` растёт от 30 к 100 ботам не более чем в ×5, а для карты —
  не более чем в ×3,3; commander и экономика — не более чем в ×1,5 мс/бот/ход.

## Последствия

+ Стоимость тика не содержит повторного полного обхода карты для каждого игрока.
+ Хэш состояния сохраняет данные, необходимые для детерминированного реплея.
− Системы должны поддерживать индексы изменений и тестовый полный пересчёт.
− Нужны тесты эквивалентности для захватов, движения, построек и дорог.
