# ADR-0016: Версии слоёв и реестр кэшей производных данных

**Статус:** принято · 2026-11-11

## Контекст
Тик сервера и воркера на 60–70% состоит из тяжёлых расчётов по всей карте (рост населения, доход, изоляция сетей, обзор, проверки ботов). Кэшировать их вручную (`markNetworkDirty`, `supplyRevision`, сигнатуры) хрупко: новая механика, которая забыла «пометить грязным», либо тихо ломает игру устаревшим кэшем, либо, наоборот, навсегда выключает ускорение. Владелец требует, чтобы оптимизация не разваливалась при добавлении функций.

## Решение
1. **Версии слоёв** (`state/layers.ts`): слои гексов (улучшения, постройки, дороги), города и сети снабжения имеют счётчик версии. Меняются слои только через функции этого файла (`setImprovement`, `setBuilding`, `setRoad`, `addCity`, `setCityLevel`, `setCityOwner`, `setHexOwner`); каждая запись повышает версию. Прямая запись в `state.hexes.<слой>[…]` запрещена ESLint в `packages/sim/src`.
2. **Реестр кэшей** (`state/derived.ts`): тяжёлый расчёт оформляется как `memo(state, ключ, слои, расчёт)` и пересчитывается только при смене версии одного из перечисленных слоёв. Состояние (`MatchState`) не расширяется: версии и кэш живут в `WeakMap`, хеш состояния и golden не затронуты.
3. **Аудит кэшей**: в тестах sim, replay и bench каждое 5-е попадание в кэш пересчитывается заново и сверяется (`configureDerivedAudit`, настройка `packages/sim/test/derived-audit.setup.ts`). Забытое повышение версии или запись в обход API падает сразу с названием кэша.
4. **Контракт производительности** (`packages/sim/test/derived-cache.test.ts`): число пересчётов проверяется счётчиками, а не временем (не зависит от машины), например маска близости к городу пересчитывается не чаще, чем появляется город.

## Последствия
+ Новая механика получает кэш одной строкой `memo`, а забытая версия ловится тестами, не игроками.
+ Обход API невозможен без нарушения линтера; в тестах допустим, но аудит отлавливает устаревание.
− Кэшируемые результаты общие: их нельзя изменять (в типах — `readonly`, в комментариях).
− Слой с высокой частотой записей (население `pop`) в этой схеме не участвует: он меняется каждый тик; для него используются таблицы и общие проходы.
