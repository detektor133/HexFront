# ADR 0014: Последовательная оркестрация в ветке этапа

## Решение

Цикл ведёт одну задачу в ветке этапа. Веток задач и worktree нет.

Порядок задачи: `plan` → приёмочные тесты → локальные атомарные коммиты → полный read-only review → исправления пакетами по владельцу → финальный полный review → сведение истории в один коммит → локальный gate → push → обязательные workflow точного SHA → служебный коммит `[x]` и `STATUS.md` → CI служебного коммита.

До первого review исполнитель получает автоматически собранную матрицу всех требований задачи. Reviewer получает ту же матрицу и возвращает все блокеры структурированными строками `КОД:` или `ТЕСТ:`. Оркестратор хранит очередь в `.ai-logs/agent-loop/state.json`, объединяет все пункты одного владельца в один проход и после коммита запускает узкий review пакета. После пустой очереди полный review проверяет весь diff задачи.

Рабочий `pnpm verify --changed` включает dependency-cruiser, поэтому нарушение архитектурных границ не откладывается до финального gate. Вычисляемые ожидания spec выводятся из документированной формулы и канонических промежуточных данных; подбор golden-чисел по результату прогона запрещён.

Задача, заблокированная вопросом `plan`, временно пропускается ради следующих автоматических задач. Дойти до задачи владельца через такой пропуск нельзя: цикл показывает список более ранних блокеров и требует `$decide`, иначе создаётся ложное впечатление, что незавершённые задачи выполнены.

Ожидание `plan-blocked` не ограничивается ссылкой на `docs/QUESTIONS.md`: консоль показывает действие `[В] ответить здесь`, последовательно выводит полный вопрос и рекомендацию для каждой заблокированной задачи, принимает рекомендацию или свободный текст и сама создаёт одну Issue `$decide`. Без этого владелец видит только внутреннее имя файла и не может понять требуемое решение из рабочего экрана.

Рабочим сессиям запрещён push hook-ом. Оркестратор дополнительно сверяет remote ref после сессии. Перед публикацией `origin/<ветка этапа>` обязан совпадать с базой задачи; автоматический rebase после review запрещён. CI выбирает последний push-run каждого проверяемого workflow по `head_sha`, `run_number` и `run_attempt`; результат другого коммита или старой попытки не принимается.

Финализация хранится отдельной фазой до изменения документов. После перезапуска оркестратор повторно вычисляет `[x]` и `STATUS.md`, сравнивает их с `HEAD` и либо завершает оборванный служебный коммит, либо переходит к его CI без дублирования.

## Причина

Параллельные ветки создали три конкурирующих источника состояния: Git, stage-файл и локальный state. Исправления накапливались в тексте задачи, а исполнитель получал сразу старые и новые требования. Последовательная очередь оставляет один опубликованный HEAD и один текущий дефект, поэтому повторный запуск восстанавливает однозначный следующий шаг.
