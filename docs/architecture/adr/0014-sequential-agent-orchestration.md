# ADR 0014: Последовательная оркестрация в ветке этапа

## Решение

Цикл ведёт одну задачу в ветке этапа. Веток задач и worktree нет.

Порядок задачи: `plan` → приёмочные тесты → локальные атомарные коммиты → полный read-only review → исправления по одному → финальный полный review → push → обязательные workflow точного SHA → служебный коммит `[x]` и `STATUS.md` → CI служебного коммита.

Reviewer возвращает все блокеры структурированными строками `КОД:` или `ТЕСТ:`. Оркестратор хранит очередь в `.ai-logs/agent-loop/state.json`, передаёт исправителю только первый пункт и после коммита запускает узкий review этого пункта. После пустой очереди полный review проверяет весь diff задачи.

Рабочим сессиям запрещён push hook-ом. Оркестратор дополнительно сверяет remote ref после сессии. Перед публикацией `origin/<ветка этапа>` обязан совпадать с базой задачи; автоматический rebase после review запрещён. CI выбирает последний push-run каждого проверяемого workflow по `head_sha`, `run_number` и `run_attempt`; результат другого коммита или старой попытки не принимается.

Финализация хранится отдельной фазой до изменения документов. После перезапуска оркестратор повторно вычисляет `[x]` и `STATUS.md`, сравнивает их с `HEAD` и либо завершает оборванный служебный коммит, либо переходит к его CI без дублирования.

## Причина

Параллельные ветки создали три конкурирующих источника состояния: Git, stage-файл и локальный state. Исправления накапливались в тексте задачи, а исполнитель получал сразу старые и новые требования. Последовательная очередь оставляет один опубликованный HEAD и один текущий дефект, поэтому повторный запуск восстанавливает однозначный следующий шаг.
