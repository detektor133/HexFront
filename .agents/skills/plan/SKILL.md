# $plan <этап/задача> | $plan <текст владельца>

Ты проверяешь и, если нужно, правишь только текст задачи — не код. Код продукта, тесты и сам цикл (`tools/agent-loop/**`, `.codex/**`) не трогаешь. Права такие же узкие, как у `reviewer`: только `docs/stages/**`, `docs/STATUS.md`, `docs/QUESTIONS.md`, `docs/DECISIONS.md`, `.ai-logs/**`.

Вызов с номером задачи (`$plan 06/T2`) — задача уже лежит в файле этапа, проверь и, если нужно, исправь её блок. Вызов с текстом владельца без номера (первая строка Issue `$plan`, дальше текст своими словами) — такой задачи в файле этапа ещё нет: превращаешь текст в блок(и) задачи с нуля по шагам 1–8 ниже, затем вставляешь их в текущий этап и очередь, как делает `$decide` с новыми задачами.

## Проверка (для задачи по номеру — её текущий блок; для текста владельца — то, что должно получиться)

1. Найди файлы, которых касается текст задачи (`rg -l`). Файл должен существовать; если задача создаёт новый файл — путь и соседние файлы должны согласовываться с `docs/architecture/*.md`.
2. Проверь каждый пункт «Приёмки»: измерим ли он числом, конкретным `файл:строка` или командой (`pnpm ...`), а не словесным описанием без ссылки («минимальное перекрытие», «удобно», «красиво» без токена).
3. Сверь формулировку с доками по таблице «механика → раздел GDD» и «что делает код → где доки» из `AGENTS.md` §1. Не выдумывай механик, чисел, цветов, шрифтов, которых там нет.
4. Если текст уже достаточный и измеримый — не трогай его.
5. Если что-то неточно, но исправимо без нового смысла (путь устарел и переехал, критерий можно сформулировать числом/токеном, который уже есть в доках) — исправь блок задачи в файле этапа, не ослабляя и не убирая ни одного пункта приёмки.
6. Если объём на деле больше одной задачи — разбей её так же, как `.agents/skills/split/SKILL.md`: подзадачи `Tna`, `Tnb`…, таблица трассировки (каждое предложение и каждый критерий исходной задачи — отдельной строкой с номером подзадачи), запреты исходной задачи копируются в каждую подзадачу, `docs/STATUS.md` — строка «Очередь» заменяет исходную задачу подзадачами по порядку.
7. Если встретился вопрос, ответа на который в доках нет, — не придумывай: запиши его в `docs/QUESTIONS.md` (формат — первая строка файла), текст задачи в файле этапа не меняй.
8. Никогда не ослабляй задачу: не упрощай критерий приёмки, не убирай пункт, не меняй «что проверяется» — только уточняешь формулировку, добавляешь недостающие числа и ссылки на доки, разбиваешь объём или останавливаешься вопросом.

Любая правка (уточнение, разбиение) или новый текст владельца, который становится задачей, — строка в `docs/DECISIONS.md`: что и почему уточнено/разбито, без изменения сути критерия.

## Коммит и ответ

Если ничего не менял (п. 4) — коммит не делай, рабочее дерево остаётся чистым.
Если правил блок задачи, разбивал её или писал новый текст владельца с нуля — один docs-коммит с трейлером `Этап: <NN>/infra`, затем push.
Если записал вопрос в `docs/QUESTIONS.md` без правки блока задачи — тоже один docs-коммит (там же трейлер `Этап: <NN>/infra`) и push: вопрос должен попасть в ветку, иначе цикл не увидит блокировку.

Ответ — не длиннее 5 строк, последняя строка ровно одна из:
- `PLAN: не трогал` — текст был достаточным, ничего не менял;
- `PLAN: уточнено` — формулировка исправлена без ослабления критериев;
- `PLAN: разбито` — задача разбита на подзадачи;
- `PLAN: вопрос` — ответа в доках нет, вопрос записан в `docs/QUESTIONS.md`, задача не передаётся исполнителю.
