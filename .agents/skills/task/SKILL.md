# $task <этап/задача>

Пример: `$task 05/T3`. Если номер не указан — остановись и спроси номер.

Строка запроса «Поток wN: ветка agent/NN-Tn …» — задачу ведёт параллельный поток агентного цикла в своём каталоге (git worktree) и своей ветке. Тогда в шаге 0 ветка сверяется с веткой из этой строки, а не с «Веткой» STATUS; шаг 11 не выполняется — `docs/STATUS.md` в потоке не меняется (блокер или ожидание владельца — строкой под задачей в файле этапа); в шаге 12 пушится ветка потока. Вызов `$task NN/Tn слияние: …` даёт поток, когда свежая ветка этапа не влилась в ветку задачи без конфликта: выполни `git merge` из запроса, разреши каждый конфликт так, чтобы сохранились изменения обеих сторон, `pnpm verify --changed`, коммит слияния с трейлером задачи, push; отметку задачи не меняй.

Вызов `$task NN/Tn CI красный: <строка CI>` даёт агентный цикл: после push этой задачи CI упал. Выполни шаги 0–1 (в шаге 1 красный CI — главная работа: найди причину по логу из `pnpm ci:wait`, исправь, `pnpm verify --changed`), затем шаги 8, 11, 12 и отчёт по шагу 13. Задачу заново не выполняй, отметку задачи не меняй. Строка `CI красный: slow …` — упал workflow `slow` (все тесты, включая тяжёлые `SLOW_TESTS` из `vitest.projects.ts`): лог — `pnpm ci:wait --workflow=slow.yml`, упавший файл запусти отдельно `pnpm exec vitest run --config vitest.all.config.ts <файл>`.

## Порядок

0. Сначала сравни текущую ветку с полем «Ветка» в `docs/STATUS.md`. Если они не совпадают, остановись и сообщи владельцу.
1. В начале выполни `pnpm ci:wait` одной командой с таймаутом 660 с для `HEAD`. Обрыв по таймауту оболочки — не блокер, повтори ожидание. Красный CI из-за кода (тесты, типы, lint) сначала исправь. Красный CI по причине вне кода (403, раннер, сеть) не исправляй инфраструктуру: запиши блокер в `docs/STATUS.md` и продолжай, если локальный `pnpm verify` зелёный. Затем проверь `git status --short`; если дерево не чистое, остановись и сообщи владельцу. Файлы из строки запроса «Приёмочные тесты NN/Tn уже в рабочем дереве» — не грязь, а тесты задачи (шаг 5). Исключение — вызов `$task NN/Tn продолжить`: агентный цикл передаёт незакоммиченную работу этой же задачи после обрыва. Тогда проверь по `git diff --stat`, что изменения относятся к задаче (иначе остановись), выполни `pnpm verify --changed`, разбери его ошибки по логу и продолжай с того шага, на котором работа остановилась.
2. Найди задачу через `rg -l`, затем прочитай её блок целиком — от строки задачи до следующей задачи — и блок родительской задачи с её запретами, без сокращений (не через `-C2`). Задачу не дроби и `$split` не предлагай: разбиение назначает только владелец. Если задача является задачей владельца (плейтест, приёмка или пометка «задача владельца»), не выполняй её и скажи: «Очередь дошла до NN/Tn — это задача владельца».
3. Контекст: раздел «Следующая сессия» в `docs/STATUS.md`, последние 10 строк `docs/DECISIONS.md`. Остальные документы — только нужные разделы через `grep -n -C5`, по таблице «механика → раздел GDD» в AGENTS.md.
4. Если в документах нет ответа на дизайн-вопрос — запиши вопросы одним списком в `docs/QUESTIONS.md`, закоммить его docs-коммитом с трейлером `Этап: <NN>/<Tn>`, запушь, выведи вопросы владельцу и остановись. Код до ответа не писать.
5. Тесты на критерии приёмки и краевые случаи. Если запрос перечисляет приёмочные тесты («уже в рабочем дереве, менять их нельзя»), это и есть тесты критериев: не меняй, не переименовывай и не удаляй их, сделай их зелёными кодом и закоммить вместе с кодом; создай код по путям и именам, которые они импортируют. Свои тесты на краевые случаи — в отдельных файлах. Приёмочный тест противоречит тексту задачи или невыполним — остановись по шагу 4 (вопрос в `docs/QUESTIONS.md`), приёмочные тесты при этом не коммить. Приёмочный тест сломан сам, а не из-за кода задачи (lint самого теста; ошибка до проверки: `ReferenceError` браузерного API в существующем коде, синтаксис, путь к существующему модулю) — тест не меняй, доделай код, не коммить и закончи ответ строками `СПЕК: <файл> — <что сломано, строка ошибки>`: агентный цикл даст `$spec` исправить тест и вернёт задачу тебе сессией `продолжить`, твоя работа останется в дереве. Так же, если возврат ревью требует изменить приёмочный тест: тест не меняй, ответ закончи строкой `СПЕК: <файл> — <что требует ревью>`. Матчи ботов внутри задачи запрещены; для задач интерфейса также запрещены ботоматчи. Итерацией считается только падение теста по проверке (`assertion`) или golden-теста. Ошибки типов, сборки, импортов, lint и prettier в коде, который пишет сама задача, итерацией не считаются — их просто исправляй. После двух неудачных итераций остановись и подготовь отчёт. Проверки тестов ради зелёного результата не меняй никогда. Исключение — тесты, которые задача прямо перечисляет как заменяемые: их заменяй тестами задачи. Если старый тест противоречит критерию задачи, а задача его не перечисляет, — остановись и спроси владельца; код под старый тест не подгоняй. Не добавляй диагностики и метрики сверх критериев. Предлагай `$accept NN/Tn` только если в критериях задачи явно указан ботоматч. Исключение: при числе скорости в критериях выполни минутный замер `pnpm --filter @hexfront/bench full-match --players=30,100 --minutes=1` и сравни с базой; хуже — коммит запрещён.
6. Минимальный код, который выполняет каждый критерий на реальном пути вызова. Заглушки, хардкод и обходной путь вместо механизма, который требует задача, запрещены. Проверка — только `pnpm verify --changed`, детали ошибок — `grep -n -C3` по логу из `.ai-logs/`, не перезапуск.
7. Перед коммитом — `pnpm verify --changed` по всем изменениям задачи: сборка, типы, lint, затронутые тесты и visual при изменении клиента или пакетов. Он обязан быть зелёным. Красный verify, включая таймаут затронутого теста, — коммит и push запрещены, задача - [ ]. Таймауты не поднимать. Полный прогон всех тестов, включая golden, делает CI после push; агентный цикл ждёт его до `$review`, а красный CI возвращает задаче.
8. Коммит по `docs/CONVENTIONS.md` с трейлером `Этап: <NN>/<Tn>`. Текст коммита — через временный файл.
9. Перед отметкой `- [~]` сверь каждый пункт «Приёмки» с отчётом задачи: у каждого пункта должны быть измерение, тест или команда и результат. Неподтверждённый пункт оставляет задачу `- [ ]`; в `docs/STATUS.md` укажи ожидаемое подтверждение и владельца команды.
10. Отметь задачу `- [~]` («ждёт ревью») в файле этапа только после полной сверки приёмки. `- [x]` ставит только `$review` в новой сессии.
11. `docs/STATUS.md`: раздел «Следующая сессия» замени (не дописывай) — что сделано, следующая задача, какие файлы читать, до 30 строк. История сессий и решений в STATUS не копится: решения — в `docs/DECISIONS.md`, итоги — в отчёт этапа.
12. Push ветки этапа. CI после push не жди.
13. Отчёт владельцу до 10 строк: что сделано, решения, которые стоит знать, следующая задача, последняя строка `pnpm verify --changed`. Про CI напиши ровно: «CI не проверен, проверится в начале следующей сессии». Не используй слова «принято» и «приёмка завершена». Последняя строка отчёта: «Запусти `$review NN/Tn` в новой сессии».

## Запрещено

- Картинки, видео, браузер, ручной `pnpm dev` и Playwright.
- Фоновые задачи с опросом: длинные команды — на переднем плане с таймаутом.
- Задачи вне текущей; найденный баг — строкой в `docs/BUGS.md` с классом по `docs/PROCESS.md`, раздел «Баги и замечания». В текущей задаче чинится только Б1, который мешает её критериям; Б2 и Б3 не чинить.
