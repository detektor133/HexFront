# $decide <решения владельца>

Решения уже приняты владельцем. Не обсуждай их и не предлагай альтернатив. При `$decide` из GitHub Issue первая строка — команда, **весь остальной текст — исходное поручение**, а не материал для пересказа. Если новое решение **явно** отменяет старое правило (например, только для ПК), это разрешённая замена: старое правило обнови в действующих документах, но сохрани независимые правила мобильной версии. Если обнаружен конфликт, который поручение явно не разрешает, перечисли его и остановись.

1. Прочитай **всё** тело поручения, включая каждую задачу, пример, подпункт «Приёмки», перечень тестов и запреты. Найди все действующие упоминания меняемых правил и констант через `rg -n` в `docs/` и затронутых скиллах; закрытые задачи и исторические решения не переписывай.
2. Обнови затронутые документы (`docs/stages/`, `docs/art/`, при изменении механики — `docs/gdd/`). Числа **баланса** — только в `docs/gdd/10-balance.md`, новые числа баланса с пометкой `[ТЮНИНГ]`; не переносить правило про баланс на геометрию UI.
3. Если решение меняет задачи — правь файл этапа. **Каждый абзац, пример, подпункт, число, список файлов тестов, запрет и критерий приёмки из Issue перенеси в соответствующую действующую задачу дословно и целиком.** Не заменяй многострочный текст коротким резюме, не оставляй критерии только в Issue или в другой задаче, не удаляй сохранённые функции (например, заголовки, счётчики, прокрутку иных компонентов) без прямого решения владельца. Заголовки Markdown можно преобразовать в заголовки задач, но текст требований и приёмки не сокращать.
   **Перед коммитом сделай проверяемую сверку 1:1:** для каждой исходной задачи проверь наличие всех её абзацев, пунктов, чисел, имён тестовых файлов и формулировок «Приёмки» в **её собственном блоке** файла этапа; проверь начало и конец каждого блока, чтобы не было обрыва. Выведи количество исходных и перенесённых пунктов. Если хотя бы один отсутствует, **не коммить и не отвечай «выполнено»**. Отдельно проверь, что `docs/art/ui.md`, трассировка и `docs/STATUS.md` не противоречат задаче.
4. Строка в `docs/DECISIONS.md` на каждое решение: дата, суть, затронутые файлы.
5. Закрой соответствующие вопросы в `docs/QUESTIONS.md`.
6. `docs/STATUS.md`: какие задачи затронуты и что делать дальше.
7. Код и тесты не трогать. Один коммит `docs:` с трейлером этапа, push. Проверить HEAD и результат CI по правилам проекта; не называть решение завершённым, пока сверка п. 3 не пройдена.
8. Отчёт владельцу до 5 строк: какие файлы и задачи изменены, результат сверки полноты по п. 3, коммит и статус CI. Не утверждай, что всё перенесено, если сверка не выполнена.
