# $review

Скилл запускается владельцем вручную в новой сессии или ролью reviewer. Прочитай блок задачи целиком и блок её родителя с запретами, без сокращений, и diff всех коммитов с её трейлером. Если запрос перечисляет приёмочные тесты (их написал `$spec` до кода), сначала сверь каждый с текстом задачи: числа, формулы, путь вызова, каждый ли критерий закрыт. Тест не совпадает с задачей или не проверяет критерий (даже если зелёный) — `ВОЗВРАТ`, строка замечания начинается с `СПЕК:`, называет файл теста и что он не проверяет; по ней тест исправит исполнитель. Если запрос говорит, что исполнитель исправлял приёмочные тесты по возврату `СПЕК:`, сверь их с текстом задачи заново: ослабленная проверка, подгонка кода под тест, скрытые элементы или заглушки ради теста — `ВОЗВРАТ`. Для каждой строки `Заменён тест: <файл>:<строка> — «<цитата>»` в коммитах задачи и для каждого изменённого существующего теста без такой строки проверь: блок задачи прямо задаёт новое поведение, новая проверка проверяет его не слабее старой, остальные проверки теста не ослаблены и не удалены; иначе — `ВОЗВРАТ` с замечанием по файлу теста. Цитата пересказывает задачу не дословно, а замена по существу верна — не `ВОЗВРАТ`, а замечание в отчёте. Полный `pnpm verify` не запускай: его выполняет CI на этом коммите. Для каждого критерия и сторожа найди тест, измерение или команду чтением. По коду проверь, что каждый критерий выполнен на реальном пути вызова, а не только во вспомогательной функции, которую вызывает тест; хардкод или обходной путь вместо механизма из задачи — `ВОЗВРАТ`. На каждый запрет выполни `rg` по изменённым файлам и приведи вывод. При критерии скорости запусти только замер `pnpm --filter @hexfront/bench full-match --players=30,100 --minutes=1` и сравни с базой задачи.

Замечание `СПЕК:` называет проверку, которой не хватает, и она должна выполняться в среде теста: jsdom не считает раскладку (`getBoundingClientRect` даёт нули, CSS-модули не применяются), в Node нет холста и `Worker`, тест идёт не дольше 4 с (тяжёлые — в `SLOW_TESTS`). Если критерий в среде теста не проверить или его может подтвердить только владелец (вид на экране, реальный телефон или браузер, ощущение от игры), это не `ВОЗВРАТ` и не ожидание: впиши в отчёт задачи строку «Проверит владелец (раунды замечаний этапа): <критерий> — <почему>», остальное проверяй как обычно. Задача владельца (в заголовке «задача владельца») по-прежнему ждёт его `$done`.

Повторное ревью (под задачей уже есть «Возврат ревью:») сходится, а не начинается заново: проверь каждый пункт прошлых возвратов и diff коммитов после последнего возврата. Новое замечание `СПЕК:` допустимо только к строкам тестов, изменённым после последнего возврата; к тестам, которые прошлое ревью уже видело и не вернуло, новых `СПЕК:` нет. Если критерий перечисляет несколько свойств (порядок, место, счёт; сортировка и группировка; и т.п.) и исполнитель менял тест на это перечисление, проверь в изменённых строках все перечисленные свойства критерия за один проход, а не только то, что называл прошлый возврат — несколько `СПЕК:` на разные свойства одного критерия в одном ответе лучше, чем растягивать их на отдельные круги. Невыполненный критерий в коде продукта, хардкод и нарушение запрета возвращаются всегда. Если запрос перечисляет строки, изменённые после прошлого возврата, — это они (цикл считает их `git diff -M`, переименованный файл не новый): `СПЕК:` к другим строкам тестов цикл отклоняет; каждое `СПЕК:` называет `файл:строки`. Не требуй вернуть то, что исполнитель изменил по прошлому возврату, если текст задачи с тех пор не менялся. Строка запроса «Текст задачи изменён после прошлого возврата» — ревью по новому тексту целиком.

Что держит задачу. `ВОЗВРАТ` — только за то, без исправления чего задача пройдёт с невыполненным критерием: критерий не выполнен в коде продукта на реальном пути вызова; хардкод или обходной путь; нарушен запрет; приёмочный тест может остаться зелёным при невыполненном критерии или не проверяет его вовсе; красный CI. Тест, который доказывает критерий, но расходится с текстом задачи в форме (имя или суффикс файла при той же среде теста, другие числа входа при проверке не слабее, порядок и группировка проверок), — не `ВОЗВРАТ`: такие пункты пиши в отчёт задачи строкой «Замечание ревью (не держит задачу): <пункт> — файл:строка». Перед каждым пунктом `ВОЗВРАТ` ответь себе: может ли задача без этого исправления пройти с невыполненным критерием? Нет — пункт в отчёт.

Первой строкой ответа напиши `OK`, если всё подтверждено, иначе `ВОЗВРАТ` и список `пункт — файл:строка — что не так`. Код и тесты не изменяй. При `OK` замени `- [~]` на `- [x]`; если это последняя подзадача после `$split` и все подзадачи родителя теперь `[x]`, отметь `[x]` и родителя. Добавь строку в отчёт и создай docs-коммит с трейлером `Этап: NN/Tn`. При `ВОЗВРАТ` замени `- [~]` на `- [ ]`, под задачей добавь строку «Возврат ревью:» со списком и создай такой же docs-коммит. В обоих случаях — push ветки.

Строка запроса «Поток wN: ветка agent/NN-Tn …» — задачу ведёт параллельный поток: работай в его ветке и пушь её; `docs/STATUS.md` не меняй. Строка «Повторное ревью после слияния ветки этапа: <причина>» — задача уже `[x]` в ветке потока, а в неё влились изменения ветки этапа; проверь diff задачи вместе со слиянием по названной причине (те же файлы, разрешённый конфликт, файлы вне «Файлы:» задачи). При `OK` отметку не меняй и коммит не делай; при `ВОЗВРАТ` — `[ ]` и docs-коммит, как обычно.
