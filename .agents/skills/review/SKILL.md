# $review

Прочитай блок задачи, родительский блок и локальный diff задачи. Проверь вместе продуктовый код,
приёмочные тесты, реальные пути вызова, критерии, запреты и регрессии. Полный `pnpm verify` не
запускай.

Reviewer работает только на чтение: не меняй файлы, stage-задачу, STATUS или Git; не коммить и
не push. Результат хранит оркестратор.

Итоговый ответ — JSON по схеме `tools/agent-loop/schemas/review.json`: `outcome` равен `OK` или `ВОЗВРАТ`; `findings` — массив. При `OK` массив пуст. При возврате перечисли все найденные блокеры сразу:

Для каждого пункта укажи `basis: "diff"`, если дефект доказан чтением текущего кода или теста, либо `basis: "gate"`, если он доказан выводом приложенной текущей проверки. Старые логи `.ai-logs` не доказывают красный gate текущего HEAD. Если оркестратор сообщил зелёный gate, не возвращай его прежнюю ошибку.

- `kind: "КОД"`, `text: "<критерий> — <наблюдаемое поведение> — <файл:строка>"` для дефекта продукта;
- `kind: "ТЕСТ"`, `text: "<файл:строка> — <минимальная регрессия, при которой тест останется зелёным>"` для теста;
- `kind: "ПЛАН"`, `text: "<критерий> — <почему его нельзя проверить разрешёнными средствами>"` для противоречивой
  или непроверяемой приёмки; не требуй от теста имитировать результат проверяемого механизма.

Поле `text` не начинай с `КОД:`, `ТЕСТ:` или `ПЛАН:`: тип уже задан в `kind`.

Каждый пункт атомарен. Оркестратор передаст замечания `КОД:` и `ТЕСТ:` одному исполнителю
одним проходом; `ПЛАН:` остаётся отдельным решением о требованиях.
При диагностике красной проверки опирайся на приложенные команды и вывод целевых тестов и verify, а не на пересказ
исполнителя. Если тест не дошёл до проверяемого поведения, назови не выполненную предпосылку,
её наблюдаемый результат и способ получить нужное состояние без имитации результата механизма.
Для UI-теста проверь, откуда взяты id, координата и открытое состояние: числовая точка или рамка,
подобранная без связи с фактическим объектом, не доказывает его выбор. Возвращай `ТЕСТ` с нарушенной
предпосылкой, даже если последняя проверка случайно зелёная. Для CSS проверяй управляемый сценарий
и доступный локатор; для взаимодействия — реальный ввод и подтверждённый выбранный объект.
Повторные формулировки одной причины объединяй в один пункт.
Перед первым полным вердиктом проверь каждый пункт приложенной матрицы требований и верни все
блокеры сразу. Если запрос требует узко проверить исправленный пакет, проверяй только его; новые
замечания оставь для финального полного review.

Исходное поручение владельца, текст текущей задачи, её родителя и действующие GDD/решения выше старых тестов и прежних
формулировок review. Если существующий тест требует противоположного поведения, это `ТЕСТ:`, а не
`КОД:`. Перед ответом удали дубли и взаимоисключающие пункты: один критерий нельзя одновременно
требовать показать и скрыть.

Локальный diff может содержать коммиты с трейлером `Этап: <другой NN/Tn>` или `Этап: NN/infra` —
они принадлежат другой задаче или служебной инфраструктуре, опубликованы отдельно и ещё не
запушены просто потому, что push происходит одним разом в конце. Это не часть диффа твоей задачи:
не читай их код, не возвращай `КОД: задача не должна изменять ...` на такой коммит — молча
пропусти его при чтении `git log`/`git diff` и смотри только коммиты с трейлером текущей задачи.

## Визуальный гейт (снимки приложены как изображения)

Если к сессии приложены изображения (сначала кадры состояния задачи из её `@layout`-сценария, затем HUD на нескольких ширинах, `tools/agent-loop/src/visual.ts`,
один раз перед push для UI-задач) — посмотри на каждое по порядку ширин, указанному в запросе.
Это не ручной браузер: снимки сняты заранее Playwright-скриптом и приложены к тебе напрямую, не
путём в тексте. Оцени глазами то, что геометрические `@layout`-тесты не видят: трансформацией
сжатый или искажённый текст/иконки, визуальный нахлёст, нечитаемые подписи, обрезанные буквы —
даже если автотесты зелёные. Если приложены кадры сценария задачи и нужного элемента нет на них, верни `kind: "ТЕСТ"` с путём сценария. Если кадров сценария нет и критерий не требует `@layout`, по общим кадрам HUD нельзя требовать снимок невидимого элемента. Иначе отчёт того же JSON-вида: `OK` или `ВОЗВРАТ` с `kind: "КОД"` (укажи ширину,
на которой виден дефект). Код не читай для этого запроса — только приложенные изображения;
ничего не меняй.
