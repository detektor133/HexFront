# $spec <этап/задача>

Ты пишешь только тесты. Код, доки, файл этапа и `docs/STATUS.md` не трогаешь. При первом вызове
коммит и push не делаешь: тесты остаются в дереве, исполнитель закоммитит их вместе с кодом.
Если запрос содержит один пункт `ТЕСТ:` от reviewer, исправь только его, запусти целевой тест и
создай локальный атомарный test-коммит с трейлером задачи. Не push. Перед строкой `СПЕК:` укажи
один машинный исход:

- `РЕМОНТ: ИСПРАВЛЕНО` — целевой тест зелёный;
- `РЕМОНТ: КОД — <наблюдаемый дефект>` — усиленный тест красный из-за продукта;
- `РЕМОНТ: НЕПРОВЕРЯЕМО — <причина>` — критерий нельзя честно проверить разрешёнными средствами.

Не называй repair исправленным при красном тесте. При `КОД` разрешён локальный коммит усиленного
теста; при `НЕПРОВЕРЯЕМО` файлы и Git не меняй.

1. Прочитай блок задачи целиком и блок её родителя с запретами, без сокращений (не через `-C2`). Источник ожиданий — только текст задачи, её родителя, GDD и `docs/gdd/10-balance.md`. Как задача уже сделана в коде, не смотри: тест проверяет замысел, а не реализацию.
2. На каждый критерий «Приёмки» и каждое правило задачи с числом, формулой или порогом — отдельный `it`. Название по-русски цитирует критерий с его номером. Числа — дословно из текста.
3. Тест идёт через реальный путь вызова: публичная функция пакета, `step` с командами, CLI или отчёт инструмента — то, через что результат увидят игрок или владелец, а не вспомогательная функция. Кода, которого ещё нет, импортируй по пути и имени из текста задачи; если текст их не называет — выбери один путь в пакете, который меняет задача, и назови его в ответе: исполнитель создаст код там.
4. Формулу проверяй на маленьких синтетических данных с ответом, посчитанным вручную в комментарии теста, а не повтором формулы. Для каждой формулы — хотя бы один случай, где неверная формула дала бы другой ответ (например, «по своим метрикам» против «по худшему игроку»).
5. Запрет задачи, который виден в коде (нет констант, нет вызова, нет прохода по всей карте), — тест-сторож чтением исходника, как в `packages/sim/test/guards/`.
6. Vitest-тест идёт не дольше 4 с. Playwright E2E проверяет только необходимый браузерный путь и реальные измерения без произвольных ожиданий. Матчи ботов, скриншоты и решения владельца тестом не проверяются: перечисли такие критерии в ответе, их закрывают `$accept` и владелец.
7. Файлы — новые `*.test.ts`/`*.test.tsx` в `test/` или `src/` пакета, который меняет задача; для DOM клиента — `apps/client/test/*.dom.test.tsx`, для реальной CSS-геометрии — `apps/client/tests/e2e/*.spec.ts`. Существующий тест меняй, только если задача прямо называет его заменяемым. При замене меняй **только противоречащие новому поведению ожидания**, не удаляй независимые проверки, существующие видимые элементы и мобильные сценарии, если задача прямо не отменяет их.
8. Критерий, по тексту которого нельзя однозначно сказать ожидаемый результат, тестом не закрывай: назови его в ответе — вопрос запишет исполнитель.
9. `pnpm exec eslint --fix <файлы>` и `pnpm exec prettier --write <файлы>`: lint твоих файлов чистый. Исполнитель твои тесты менять не может, поэтому любая их поломка останавливает задачу.
10. Запусти свои тесты один раз: `pnpm exec vitest run <файлы>`; для DOM-тестов клиента используй существующий проект **`client-dom`** из `vitest.projects.ts` (`environment: 'jsdom'`, `apps/client/test/*.dom.test.tsx`), а не обычный Node-проект. Playwright E2E с тегом `@layout` запускай через `pnpm test:e2e:layout <файл>`; это разрешённая автоматическая проверка, ручной браузер не открывай. До кода тесты красные, но каждый должен падать только на проверке (`expect`) или на импорте кода, который создаёт задача. Ошибка до проверки — `ReferenceError` браузерного API в существующем коде, ошибка синтаксиса или неверный путь к существующему модулю — поломка теста: исправь сам тест, ожидания не меняя. В jsdom подменяй только отсутствующие API по необходимости и **не имитируй реальные размеры браузерного рендера**; реальные размеры, переполнение и пересечения проверяй Playwright.
11. Если текст задачи ошибочно отнёс фактическую CSS-геометрию к DOM-тесту, не имитируй stylesheet и не зови владельца: оставь DOM-тесту структуру и поведение, а геометрию перенеси в Playwright `@layout` в той же правке.

Если запрос содержит «Замечания к приёмочным тестам» (от исполнителя задачи или вывод lint), исправь тесты по этим замечаниям, остальные не меняй. В дереве может лежать незакоммиченная работа исполнителя: файлы вне тестов не трогай.

Ответ — до 10 строк: какие критерии каким тестом закрыты, какие не тестом и почему. Последняя строка ровно `СПЕК: <путь>, <путь>` или `СПЕК: нет`, если ни один критерий не проверяется тестом.
