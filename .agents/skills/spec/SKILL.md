# $spec <этап/задача>

Ты пишешь только тесты. Код, доки, файл этапа и `docs/STATUS.md` не трогаешь. При первом вызове
коммит и push не делаешь: тесты остаются в дереве, исполнитель закоммитит их вместе с кодом.
Если запрос содержит пакет пунктов `ТЕСТ:` от reviewer, исправь весь пакет, запусти целевые тесты и
создай локальный атомарный test-коммит с трейлером задачи. Не push. Сообщи, какие тесты запускал
и на чём они упали. Оркестратор сам повторно запускает их и передаёт красные проверки независимому
reviewer для классификации между дефектом теста, продукта и критерия. Текст ответа `$spec` не
управляет этим переходом.

1. Прочитай блок задачи целиком и блок её родителя с запретами, без сокращений (не через `-C2`). Источник ожидаемого поведения — текст задачи, её родителя, GDD и `docs/gdd/10-balance.md`. Существующий код, публичные типы, тестовые фикстуры и маршруты приложения читай для установления реального пути вызова и способа подготовки состояния; текущее поведение кода не меняет ожидание теста.
   Пункт reviewer не меняет источник истины. Если он требует поведения, противоположного задаче,
   тесты не меняй и назови противоречащий критерий в ответе.
2. На каждый критерий «Приёмки» и каждое правило задачи с числом, формулой или порогом — отдельный `it`. Название по-русски цитирует критерий с его номером. Числа — дословно из текста.
3. Тест идёт через реальный путь вызова: публичная функция пакета, `step` с командами, CLI или отчёт инструмента — то, через что результат увидят игрок или владелец, а не вспомогательная функция. Сначала найди существующий маршрут и точку входа; отсутствующий API можно назвать в тесте только если он прямо задан задачей. Не выдумывай экспорт, адрес страницы, id объекта или координаты ради теста.
4. Формулу проверяй на маленьких синтетических данных с ответом, посчитанным вручную в комментарии теста, а не повтором формулы. Результат, зависящий от существующего механизма или состояния после тика, запрещено угадывать, подбирать прогоном и фиксировать произвольным golden-числом: получи канонические промежуточные данные через публичный механизм на том же состоянии и выведи ожидание из документированной формулы. Если точное число до реализации недоступно, проверяй документированный инвариант или отношение без придуманного числового литерала; если и они не определены документами — назови критерий неоднозначным по п. 8. Для каждой формулы — хотя бы один случай, где неверная формула дала бы другой ответ (например, «по своим метрикам» против «по худшему игроку»).
5. Запрет задачи, который виден в коде (нет констант, нет вызова, нет прохода по всей карте), — тест-сторож чтением исходника, как в `packages/sim/test/guards/`.
6. Playwright E2E проверяет только необходимый браузерный путь и реальные измерения без произвольных ожиданий. Матчи ботов, скриншоты и решения владельца тестом не проверяются: перечисли такие критерии в ответе, их закрывают `$accept` и владелец.
7. Файлы — новые `*.test.ts`/`*.test.tsx` в `test/` или `src/` пакета, который меняет задача; для DOM клиента — `apps/client/test/*.dom.test.tsx`, для реальной CSS-геометрии — `apps/client/tests/e2e/*.spec.ts`. Существующий тест меняй, только если задача прямо называет его заменяемым. При замене меняй **только противоречащие новому поведению ожидания**, не удаляй независимые проверки, существующие видимые элементы и мобильные сценарии, если задача прямо не отменяет их. Целиком удалить файл можно только по пункту reviewer, который называет этот путь, когда файл содержит ровно один отменённый `it`/`test`, а строка `СПЕК:` называет существующий тест-замену.
8. Критерий, по тексту которого нельзя однозначно сказать ожидаемый результат, тестом не закрывай: назови его в ответе — вопрос запишет исполнитель.
9. `pnpm exec eslint --fix <файлы>` и `pnpm exec prettier --write <файлы>`: lint твоих файлов чистый. Исполнитель вправе исправить ошибочную фикстуру или ожидание по критерию задачи в том же рабочем проходе.
10. Запусти свои тесты один раз: `pnpm exec vitest run <файлы>` и typecheck пакета теста. Ошибки типизации внутри самого теста исправь; ожидаемое отсутствие создаваемого задачей API явно отдели от дефекта теста. Для DOM-тестов клиента используй существующий проект **`client-dom`** из `vitest.projects.ts` (`environment: 'jsdom'`, `apps/client/test/*.dom.test.tsx`), а не обычный Node-проект. Playwright E2E с тегом `@layout` запускай через `pnpm test:e2e:layout <файл>`; это разрешённая автоматическая проверка, ручной браузер не открывай. До кода тесты красные, но каждый должен падать только на проверке (`expect`) или на импорте кода, который создаёт задача. Ошибка до проверки — `ReferenceError` браузерного API в существующем коде, ошибка синтаксиса или неверный путь к существующему модулю — поломка теста: исправь сам тест, ожидания не меняя. В jsdom подменяй только отсутствующие API по необходимости и **не имитируй реальные размеры браузерного рендера**; реальные размеры, переполнение и пересечения проверяй Playwright.
   Если общий `pnpm verify --changed` падает в файле вне тестов твоей задачи, всё равно запускай разрешённые целевые Vitest и Playwright-проверки своих файлов. В ответе отдели их результат от посторонней ошибки typecheck; не объявляй критерий `НЕПРОВЕРЯЕМО` только из-за неё.
   Если целевой тест падает до проверки из-за неоднозначного локатора или ошибочной фикстуры, исправь тест и повтори целевой прогон. Отсутствующую локализацию и ещё не реализованную кнопку или обработчик назови дефектом продукта, не подменяя ожидание теста.
11. Если текст задачи ошибочно отнёс фактическую CSS-геометрию к DOM-тесту, не имитируй stylesheet и не зови владельца: оставь DOM-тесту структуру и поведение, а геометрию перенеси в Playwright `@layout` в той же правке.
12. Ожидаемый текст интерфейса бери из действующего словаря локализации или публичного форматтера.
Не пиши строку или regex по памяти. Если критерий требует причину, но не фиксирует дословный текст,
проверяй связанную доступную подпись и непустую локализованную причину, а не придуманную фразу.

Для UI-сценария сначала докажи предпосылки отдельными проверками: нужный игрок и объект существуют,
объект выбран, нужная карточка открыта и относится именно к нему. Координаты действия получай из
данных объекта и действующей функции преобразования карты; литералы `{x, y}` и случайная рамка по
экрану не являются способом найти отряд. Для проверки CSS открой управляемое состояние через
существующий dev-маршрут и найди элемент по доступному имени. Для проверки выбора используй реальный
путь ввода и проверь выбранный id до действия, которое тестируется. Если такой сценарий нельзя
подготовить, сначала назови отсутствующий тестовый шов; не подменяй выбор вызовом обработчика,
результат которого и является предметом теста.

Если запрос содержит «Замечания к приёмочным тестам» (от исполнителя задачи или вывод lint), исправь тесты по этим замечаниям, остальные не меняй. В дереве может лежать незакоммиченная работа исполнителя: файлы вне тестов не трогай.

Ответ — до 10 строк: какие критерии каким тестом закрыты, какие не тестом и почему. Последняя строка ровно `СПЕК: <путь>, <путь>` или `СПЕК: нет`, если ни один критерий не проверяется тестом.
